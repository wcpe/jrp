# 决策对齐

## 1. 动手前读取

实质改动前按影响范围阅读：

- `docs/PRD.md`：需求、阶段和验收。
- `docs/ARCHITECTURE.md`：模块、数据和机制。
- `docs/PROTOCOL.md`：兼容数据协议。
- `docs/API.md`：管理与 Agent 契约。
- `docs/adr/*`：既有重大决策。
- `.claude/rules/architecture-invariants.md` 与 `scope-discipline.md`：硬边界。

## 2. 不静默推翻

方案若与已接受 ADR、PRD、架构或协议相悖，停止实现并明确冲突。架构决策变化必须先新增 ADR 取代旧决策，经确认后再同步代码和规则；不得通过局部实现暗中改变方向。

## 3. 可追溯与精准修改

- 每处改动必须追溯到 PRD 需求、功能 spec 或明确缺陷。
- 只修改完成目标所必需的文件和代码，不顺手重构或格式化无关区域。
- 发现无关问题可报告，不擅自扩大范围。
- 引入新第三方依赖前说明用途、现有依赖为何不足，并等待确认。

## 4. 独立兼容检查

涉及官方 frpc 兼容时，先确认固定参考提交未漂移。允许研究公开线上行为，禁止复制源码、注释、错误文案、目录结构、策略表和测试组织；实现和测试必须使用 JRP 自有表述。

## 5. 模糊即停

需求、边界、兼容行为或安全取舍存在多种合理解释时，先列出差异并询问，不凭空选择。能从已批准 PRD、ADR 或 spec 唯一确定时，按真源直接执行。
