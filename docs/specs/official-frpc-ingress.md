# 功能规格：官方 frpc 接入

> 状态：草拟 · 关联 PRD：FR-03 · 分支：feature/official-frpc-ingress

## 1. 背景与目标

JRP 的产品价值之一是让已经部署官方 frpc 的用户无需更换客户端即可接入 JRP 服务端。FR-03 要求 `jrps` 能在固定兼容基线下接受官方 frpc 的连接，完成登录、心跳、代理注册与工作连接转发。

本规格解决的具体问题是：官方 frpc 是一个**外部黑盒二进制**，它使用 JRP 不控制的配置文件、不受 JRP 管理通道约束、也不会回报 JRP 私有状态。服务端必须在只依赖兼容数据协议的前提下，与它建立可判定、可观测、可排障的完整生命周期，同时严格避免把 JRP 私有管理能力混入这条通道。

使用者：jrps 运维者（管理员）、Core 的服务端会话路径，以及需要在真实网络中验证互操作的验收人。所属阶段：P1。

## 2. 需求

- `jrps` 在同一服务端入口接受官方 frpc 的连接建立，并完成 wire 版本判定。
- 支持官方 frpc 的登录与鉴权：校验客户端身份、独立 token、时间窗口与重放边界。
- 支持已认证控制会话的心跳：验证会话归属，处理抖动与超时。
- 支持代理注册：校验字段、权限、端口/域名冲突与 P1 范围，创建数据面资源，成功响应只在资源可用后返回。
- 支持工作连接：请求工作连接、校验运行身份归属、绑定目标代理、进入透明转发。
- 官方 frpc 的行为边界必须明确：它只使用兼容数据协议和自身配置，不参与 JRP 私有管理通道，服务端不得向其下发 JRP 私有命令。
- 互操作矩阵覆盖 FR-05a / FR-05b / FR-05c 全部连接传输与 FR-06a / FR-06b 全部代理类型。
- 验收以固定基线官方 frpc 二进制的黑盒互操作为准；测试全绿不能替代实机验证。

- 范围内：官方 frpc 的连接建立、登录、心跳、代理注册、工作连接、拒绝与清理路径，以及黑盒互操作矩阵的设计与证据留存。
- 范围外：
  - **「JRP 客户端连接官方 frps」这一反向兼容方向，本轮明确不做**，不在本规格中留任何设计钩子、配置项或测试占位。
  - 官方 frpc 的 enrollment、desired state 下发、配置版本回执等 JRP 私有管理能力（属于 FR-08，走独立 HTTPS/WSS 管理通道）。
  - 向官方兼容消息中新增 JRP 私有管理命令或私有字段。
  - P2 的 SUDP、TCPMUX、剩余参数与插件能力（FR-18 / FR-19）。
  - P3 的数据节点、节点 RPC、选举、分布式锁、共享数据库、租户、RBAC、OIDC。

## 3. 设计

### 3.1 兼容方向是单向的

本规格只实现「jrps / Core 服务端接收官方 frpc」这一方向。服务端不实现任何「作为 frpc 连接官方 frps 兼容服务端」的代码路径、配置项或文档承诺。理由：JRP 的价值方向是让既有客户端迁入 JRP 控制面，反向兼容既不服务该目标，也会把「JRP 需要跟随外部服务端行为」的维护负担引入 Core。

### 3.2 独立实现与取证基线

兼容研究以参考源码仓库的固定 Git 提交 `e1f1d6ab1b591ec9b596f4b1b6a81cd2960c6314` 为只读基线，遵循 ADR-0010（取代 ADR-0001）。本规格不重复其决策正文，只落地以下工程后果：

- Core 依赖图不得出现参考实现的 Go package。
- 不复制参考仓库的注释、错误文案、目录结构或测试组织。
- 所有兼容事实以 JRP 自有规格 + 黑盒证据建立。
- 临时抓包、对比结果和官方二进制只放在忽略的临时目录，不得入库。

### 3.3 模块与依赖方向

- `jrps` 装配 Core 提供的服务端门面，并把 SQLite 中的客户端与代理配置转换为 Core 的不可变快照。
- Core 只接收快照、返回运行事件与应用结果，不感知 SQLite、管理 API、Web 或通知（ADR-0002、ADR-0003）。
- 官方 frpc 与 jrpc 共用同一条兼容数据协议路径；两者的差异只体现在 jrpc 额外走独立管理通道，不体现在兼容消息族上。

### 3.4 连接建立与登录

时序遵循 `docs/PROTOCOL.md` §6.1：

1. 官方 frpc 完成连接传输建链与 wire 版本判定（见 FR-04 规格）。
2. 客户端发送登录消息，携带客户端版本、平台、身份、基于独立 token 的鉴权时间材料、运行 ID、客户端 ID、元数据与连接池摘要；线上字段为 `client_id`、`privilege_key`、`timestamp`（Unix 秒）、`run_id` 及其余诊断字段。鉴权材料是 `md5(token ∥ 十进制时间戳)` 的十六进制——官方客户端不发明文，服务端必须持有 token 明文才能复算（例外登记见 PROTOCOL §11.1）。
3. 服务端按顺序校验：客户端状态 → token 匹配 → 时间窗口 → 重放边界 → wire 能力。
4. 校验成功后分配并确认运行 ID，进入已认证控制会话；任一校验失败返回稳定失败类别并关闭连接。

鉴权失败只回显类别，不回显 token、签名、完整时间材料或内部校验细节（`docs/PROTOCOL.md` §11）。

同一客户端的重连与旧会话竞争必须有确定规则：不允许两个会话无约束地同时拥有同一代理集合。本规格采用「新会话提交登录时，旧会话进入排空；旧会话若在排空上限内未退出则被强制清理」的判定，具体阈值在会话规格中量化。

**官方 frpc 只参与此兼容登录。** jrpc 的 enrollment 与 desired state 下发不经过该消息族。

### 3.5 心跳

时序遵循 `docs/PROTOCOL.md` §6.2：

- 已认证控制会话按协商/配置周期发送心跳。
- 心跳必须验证会话归属与必要鉴权材料；归属不符的心跳直接关闭会话。
- 超过失活阈值后关闭控制会话，并进入代理与工作连接的清理流程。
- 网络抖动、单次丢失、超时边界由状态机测试覆盖，禁止无限等待或无界重试。

### 3.6 代理注册

- 客户端在登录成功后提交代理定义。
- 服务端先做字段校验、权限校验、端口/域名冲突校验与 P1 范围校验，再创建数据面资源。
- 成功响应只在资源可用后返回；失败不得留下半注册监听器或路由。
- 收到明确属于 P2 的能力（SUDP、TCPMUX、未支持插件）时，返回可判定的不支持错误，而不是部分应用（`docs/PROTOCOL.md` §5）。
- 关闭代理后停止接收新流量，活动连接按生命周期排空。

### 3.7 工作连接

时序遵循 `docs/PROTOCOL.md` §7：

1. 服务端根据待处理用户流量向已认证客户端请求工作连接。
2. 官方 frpc 建立新的同类连接传输，完成 wire 选择并声明其运行 ID 与鉴权材料。
3. 服务端验证工作连接属于当前控制会话，随后发送目标代理与源/目标摘要。
4. 双方完成可选加密、压缩或限速包装后进入透明转发。
5. 无效运行 ID、过期会话、重复绑定、未知代理或超时连接必须拒绝并释放资源。

工作连接池必须有上限与回收策略；任何网络 IO、SQLite 或通知调用不得在持有全局会话锁时执行。

### 3.8 互操作矩阵

矩阵覆盖 **FR-05a（TCP）、FR-05b（WebSocket 与 WSS）、FR-05c（KCP 与 QUIC）** 三种传输规格与 **FR-06a（TCP、UDP、HTTP、HTTPS）、FR-06b（STCP、XTCP）** 两种代理规格的全部声明组合，与 `docs/PROTOCOL.md` §9 的矩阵一致。

分层测试策略：

1. **传输层门禁**：每种传输先通过 wire 与会话基础测试，证明控制连接可建立、心跳可持续。
2. **代理层语义**：每种代理在一种代表性传输上完成完整语义测试。
3. **组合层抽样**：关键组合（HTTPS 透传 × WSS、UDP × KCP）与全部声明组合通过自动化或真实互操作抽样门禁。
4. **实机层**：XTCP 与所有涉及真实 NAT 的组合必须由用户在真实网络环境确认通过。

### 3.9 黑盒互操作测试做法

- **被测二进制**：下载官方 frpc 发行二进制（按目标平台选择），保存到忽略的临时目录，不入库、不纳入 Git。基线提交在上游公开仓库不可检出，被测版本按依赖区间推定为 **v0.70.0**（依据与发行包摘要见 PROTOCOL §1 与黑盒脚本登记表）。摘要登记表 `scripts/compat/frpc.mjs` 只收录已核验的平台：Windows 与 Linux 的 amd64 摘要均与官方发行附件 `frp_sha256_checksums.txt` 逐字符一致，未登记的平台会被直接拒绝运行。CI 的 `compat-interop` job 在 Linux runner 上复跑本矩阵，因此 Linux 运行时同样在门禁内。
- **被测服务端**：本地构建 jrps，使用临时数据目录与临时 SQLite，避免污染开发数据。
- **用例组织**：每个用例是一组「frpc 配置片段 + 期望观测」，由脚本生成 frpc 配置、启动 frpc、等待 jrps 事件、访问入口地址、断言结果、最后清理进程。
- **强制版本**：分别强制 wire v1 与 wire v2 发起连接，两者都必须通过。
- **实机验收执行器**：真实网络/NAT/反向代理批次由 `scripts/compat/real-network.mjs` 执行——它以远端 jrps 为目标，先做可达性预检（TCP 可达、WSS 证书链、KCP/QUIC 的 UDP 探测），再断言登录、代理注册、入口回显、观察期心跳稳定与客户端重启后重新登录，并把必须由人观察的项目（NAT 类型、反向代理、跨运营商、跨平台）写成待回填报告，产物落 `.tmp/compat-real/<日期>/<传输>-<wire>/`。该执行器已在本机对 TCP、WebSocket、WSS、QUIC 自测通过。它另有只读预检模式 `--preflight-only`：只做可达性、证书链与入口端口现状探查，不启动客户端、不注册任何代理、不需要数据面凭据，用于在正式批次之前确认目标环境是否具备执行条件（预检结论不构成验收结论）。执行命令、参数表与人工回填清单见 `docs/OPERATIONS.md` §6，等价快捷入口为 `task compat:real-network -- <参数>`；全部参数亦可以 `--help` 就地查看。
- **覆盖场景**：登录成功、登录失败、心跳超时、代理注册冲突、工作连接绑定、访客鉴权、NAT 结果（`docs/PROTOCOL.md` §12）。
- **NAT 探测工具**：`scripts/compat/nat-probe.mjs` 用 RFC 5389 binding 请求从同一本地 UDP 端口向多个目的地址探测，比较外部端口是否一致以判定客户端侧映射方式（端点无关／地址相关），供实机批次回填「NAT 类型与端口映射方式」。它内置应答器（`--serve`）可离线自测，默认不联网；只发 binding 请求，不注册代理、不需要凭据。本机实测可判定（3/4 端点应答，判定为端点无关映射），说明该工具在真实 NAT 后可用。

### 3.10 证据留存

- 证据产物目录：忽略的临时目录下的 `compat/<日期>/<用例名>/`，包含 frpc 配置、jrps 日志片段、事件断言输出、入口访问结果与退出码。
- 官方二进制与解压产物只保留在该目录，不写入仓库任何位置。
- 总结报告记录：基线提交、被测平台、用例清单、通过/失败、失败时的可观测错误类别。
- **证据产物不得入库**；入库的是被证据钉住后写入 `docs/PROTOCOL.md` 与 Core 测试向量的行为事实。

## 5. 验收标准

正常路径：

- 固定基线官方 frpc 在 wire v1 与 wire v2 下均能完成登录并进入已认证控制会话。
- 官方 frpc 注册的代理能在 jrps 入口被正常访问，数据双向可达。
- 心跳周期内会话保持；代理注销后入口停止接收新流量，活动连接排空。

边界：

- 端口/域名冲突的代理注册返回明确冲突错误，已有代理不受影响。
- 连接池达到上限时新工作连接请求被推迟或拒绝，且有可观测事件，不悬挂。
- 心跳单次丢失后会话恢复，连续丢失超过失活阈值后会话关闭并清理。

错误路径：

- token 不匹配、时间窗口外、重放、wire 能力不足四类登录失败均返回稳定类别，响应与日志均不回显 token、签名或完整时间材料。
- 无效运行 ID、过期会话、重复绑定、未知代理的工作连接被拒绝并释放资源，不泄漏 goroutine 与连接。
- 官方 frpc 提交 P2 能力时收到不支持错误，且服务端不存在半注册监听器或路由。

矩阵与实机：

- FR-05a / FR-05b / FR-05c 传输与 FR-06a / FR-06b 代理的声明组合全部纳入矩阵执行，结果逐项记录。
- **涉及真实网络 / NAT 的结果（尤其是 XTCP 打洞、WSS 证书链、KCP/QUIC 公网路径）必须由用户在真实环境确认实机通过；自动化测试全绿不能替代实机验收。**
- 证据产物完整保存在忽略的临时目录，仓库中不含官方二进制、抓包或临时报告。

### 5.1 验收现状（自动化部分）

Core 已接入 TCP、WebSocket/WSS、KCP、QUIC 的配置、内部适配和客户端/服务端传输选择；Core 与 jrps/jrpc 测试、传输适配竞态测试通过。官方 frpc v0.70.0 黑盒脚本已扩展为 v1/v2 矩阵，当前四类 P1 代理与拒绝/失活场景均已获得端到端证据。

当前官方 frpc 代理用例黑盒结果（2026 年 9 月 27 日最近一次执行；v1/v2 共 20 项，20 项通过、0 项失败）：

| 用例 | v1 | v2 | 对应条款 |
|---|---|---|---|
| 登录并进入已认证控制会话 | ✅ | ✅ | 正常路径第 1 条 |
| TCP 代理入口可达、双向回显逐字节一致 | ✅ | ✅ | 正常路径第 2 条 |
| HTTPS 透传入口可达、字节流回显 | ✅ | ✅ | FR-06a HTTPS 透传 |
| 鉴权材料错误被拒、无已连接事件 | ✅ | ✅ | 错误路径第 1 条（token 类） |
| P2 STCP 注册被拒且无成功注册 | ✅ | ✅ | 错误路径第 3 条 |
| 无效运行 ID 的工作连接被拒 | ✅ | ✅ | 错误路径第 2 条 |
| 端口冲突后客户端自动换端口仍注册成功 | ✅ | ✅ | 边界第 1 条（冲突不致命向） |
| HTTP vhost 数据面 | ✅ | ✅ | HTTP 主机/路径路由与目标响应 |
| UDP 数据面 | ✅ | ✅ | 官方 udp-packet JSON 与 JRP wire v1/v2 封装 |
| 心跳失活 relay | ✅ | ✅ | relay 丢弃客户端心跳、官方客户端超时、服务端清理 |

运行时代理协议级测试与官方二进制端到端测试均覆盖 TCP、UDP、HTTP、HTTPS 注册资源、共享 HTTP 路由、HTTPS 透传、心跳失活清理、工作连接拒绝和会话归属清理。

连接传输矩阵（每项为「登录 + TCP 代理端到端回显」，jrps 按 desired 的 `controlListen.transport` 启动对应控制入口）：

| 传输 | v1 | v2 | 说明 |
|---|---|---|---|
| TCP | ✅ | ✅ | FR-05a |
| WebSocket | ✅ | ✅ | 路径与官方客户端一致（`/~!frp`） |
| WSS | ✅ | ✅ | 自签证书 + IP SAN，指纹/信任根校验通过 |
| QUIC | ✅ | ✅ | ALPN `frp`；控制连接与工作连接是同一会话上的两条流 |
| KCP | ⚪ 基线限制 | ⚪ 基线限制 | 已登记为基线客户端限制，不计入 P1 互操作门禁，见下方取证 |

**KCP 行的基线限制登记（2026 年 9 月 27 日，经用户确认）**：固定基线官方 frpc v0.70.0 在 `transport.protocol = "kcp"` 下**不发出任何数据报**。取证覆盖三条独立路径：

1. 本机 UDP 抓包探针在 12–15 秒窗口内收到 0 个报文（默认配置、`tls.enable=true`、`tcpMux=true` 三种组合均如此）。
2. 同一配置指向官方 frps v0.70.0（`kcpBindPort` 监听、`log.level=trace`）时，服务端日志只有启动三行、没有任何客户端连接。
3. 官方二进制自身的 `frpc verify` 判定该配置合法，`transport.protocol` 的取值列表在 v0.70.0 中确实包含 `kcp`。

JRP 侧能力已独立确认：控制入口按 desired 就绪（服务端日志「控制入口已就绪 传输=kcp 地址=[::]:7200」），裸 KCP 客户端（与官方同参：FEC 10/3、stream 模式、MTU 1350）可建立会话并被 jrps 接收，且以自有客户端经该入口完成真实登录（服务端记录「控制连接首帧 类型=login」）。因此该行属基线客户端行为，非 JRP 缺陷。

**处理结论**：该行登记为**基线客户端限制**，不计入 P1 互操作门禁；JRP 自身 KCP 由引擎级端到端用例（控制会话建立、通配监听 + IPv4 拨号）与传输适配单测覆盖。若后续引入可用的基线客户端，必须在保留本登记的前提下补跑该行并留存证据。

**公网实机批次已完成（2026-09-27，服务端为原生公网地址的 Linux 主机，客户端为 NAT 后的 Windows）**：tcp / websocket / quic 三种控制入口传输 × wire v1/v2 共 6 项全部通过，五项断言（登录、代理注册、入口回显逐字节一致、观察期心跳稳定、重启后重新登录）全绿；覆盖 Windows 客户端 ↔ Linux 服务端的真实跨端组合与跨运营商/跨境链路。KCP 因基线客户端限制不在批次内；WSS 由本机真实 nginx 终结 TLS 拓扑覆盖。完整报告（含执行者回填项与三项按设计生效的行为）见 `.tmp/fr03-closeout/real-acceptance/REPORT.md`（证据不入库）。

实机同时暴露并修复一处外壳缺陷：`jrps` 的启动恢复路径也执行「控制入口身份比较」，而比较基准是上次记录的 active——重启时引擎已按最新 desired 建立新监听，于是把重启本应生效的新身份判为非法变更，入口永远停在旧传输（desired 由 tcp 改为 websocket 后重启即复现）。恢复现已跳过该守卫，热更路径的守卫不变（回归用例 `TestRecoverAppliesChangedBootstrapIdentity`）。

实机批次的前置验证已完成（本机链路夹具 `scripts/compat/link-fixtures.mjs`）：

- **反向代理升级路径**：WebSocket 经本地 HTTP 反向代理（升级透传）执行双 wire 验收，v1/v2 均通过；该验证同时暴露并修复了控制会话接管的登记竞态（见 CHANGELOG「变更」）。更进一步，**真实反向代理软件**已按三种拓扑实测（nginx 1.28.3，`proxy_read_timeout` 默认 60s，显式透传 `Upgrade`/`Connection`）：**L4 stream 透传**下 tcp 传输全部 10 个用例 × 双 wire 共 20/20 通过；**L7 明文反代**下 websocket 传输 16/20 通过、4 项 blocked（`heartbeat-relay` 与 `work-conn-rejected` 依赖裸 TCP 帧或本机中继，仅在 tcp 传输下可执行，已按 blocked 如实登记而非计失败）、0 失败；**L7 终结 TLS**（前端 wss、后端明文 ws）下登录与入口回显双 wire 4/4 通过。反代空闲读超时与心跳间隔的关系也已量化：心跳 90s（大于反代 60s 超时）时 nginx 在 60s 空闲后切断升级连接（`upstream timed out … while proxying upgraded connection`），官方客户端用同一 runID 自动重连，服务端侧会话事件由 1 次变 2 次；心跳 30s（官方默认，小于反代超时）时同一窗口内反代零超时、会话事件恒为 1 次。结论：**反代空闲超时必须大于客户端心跳间隔**，nginx 默认 60s 对默认心跳是安全的。
- **高延迟链路**：每分片 40ms 延迟下双 wire 验收通过，说明控制会话与工作连接对延迟不敏感。
- **连接建立被丢弃**：按 10% 概率丢弃新建连接时，官方客户端在期限内未能完成登录/重连并退出，脚本如实报告失败——这属客户端重试策略与链路质量的交互，需在真实弱网中确认。
- **UDP 载体（QUIC）丢包与延迟**：经 UDP 中继（`--mode=udp`）执行 QUIC 双 wire 验收，20ms 延迟通过；叠加 5% 与 15% 数据报丢弃仍通过，说明丢包由 QUIC 自身恢复，控制会话与工作连接均可承载。UDP 中继上按概率丢弃数据报是丢包的忠实模型（UDP 无重传）。
- **NAT 式空闲回收**：中继在 4 秒无流量后丢弃对端映射（下一次数据报用新的上游端口重建，等价于 NAT 表项回收后源端口变化），叠加 20ms 延迟 + 30ms 抖动 + 5% 丢包，QUIC v1 验收通过；夹具统计确认该轮实际发生 2 次映射回收、2 个数据报丢弃、85 个数据报转发，说明 QUIC 能在映射被回收后自行恢复会话。真实 NAT 设备的行为（表项时长、对称 NAT、端口受限）仍须实机确认。
- **客户端离线后入口停止接收新流量**（对应正常路径第 3 条）：用 `scripts/compat/client-loss.mjs` 逐传输测量——强杀官方客户端后，流传输几乎立刻停止接受新连接（tcp 511ms、websocket 510ms、wss 509ms，测量轮询间隔 500ms），QUIC 为 30140ms（等于其会话空闲超时）。该差异是传输固有语义：流传输能立刻感知连接断开，UDP 载体只能等会话空闲回收；30 秒短于控制会话对「进程存活但心跳停止」的失活窗口（默认心跳 30s × 3 = 90s），期间新访客受配对中心暂存上限约束，不会无界堆积。真实网络中的 NAT 空闲表项时长仍须实机确认。

夹具的方法论边界：它在 TCP 之上转发，**不能**用丢字节模拟丢包（会不可恢复地破坏字节流，把夹具自身破坏误报为实现失败），因此只提供「固定延迟」与「新建连接丢弃」两类忠实手段；真实丢包率、抖动、NAT 空闲回收仍必须由用户在目标环境确认。反向代理一项已用真实 nginx 软件覆盖（见上），夹具保留为可复现的回归手段。

服务端的「冲突返回明确错误」由协议级单测覆盖：官方客户端会在端口冲突后自动换端口重试，把首次拒绝掩盖掉，黑盒侧观测不到该拒绝本身。

## 6. 风险与待定

- **官方二进制获取与环境依赖**：固定基线的官方 frpc 发行二进制需从官方发布渠道下载，下载产物与校验值只留在忽略的临时目录；离线环境无法执行黑盒矩阵，需要用户在联网环境执行并记录结果。
- **FR-05b 与 FR-05c 的依赖已获用户批准并接入 Core**：WebSocket、WSS、QUIC 的官方客户端互操作已在本机复现通过；KCP 因基线客户端不发流量而无法驱动（取证见 §5.1）。**跨平台与真实网络均已收口**：CI 的 `compat-interop` job 以 Linux 运行时复跑互操作矩阵（官方 frpc Linux 发行包摘要取自官方 `frp_sha256_checksums.txt` 并登记在 `scripts/compat/frpc.mjs`）；公网实机批次于 2026-09-27 在原生公网地址的 Linux 服务端与 NAT 后的 Windows 客户端之间完成，tcp / websocket / quic × wire v1/v2 共 6 项全部通过（报告见 `.tmp/fr03-closeout/real-acceptance/REPORT.md`，证据不入库）。
- **控制入口传输需要重启生效**：`controlListen` 的地址、端口、传输方式与 TLS 材料属引导身份，应用流程会显式拒绝其变更并保留旧 active（详见 `docs/OPERATIONS.md`）。
- **版本强制手段需取证**：如何用配置强制官方 frpc 走 wire v1 而非 v2，需要在黑盒运行中确认；若官方二进制不提供稳定的强制开关，则改为通过服务端「仅 v1」入口间接验证，并在报告中说明。
- **旧会话排空阈值未量化**：排空上限的具体取值与会话冲突处理需要在会话规格中定义，本规格只约束「必须确定、不允许双持」。
- **实机验收是硬门槛**：XTCP 与真实 NAT 场景的结果无法由 CI 证明，必须由用户在目标网络环境确认。
