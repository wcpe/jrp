# 功能规格：客户端令牌管理

> 状态：草拟 · 关联 PRD：FR-07 · 分支：feature/client-token-management

## 1. 背景与目标

管理员需要为每个客户端单独发放凭据，才能在某个客户端失陷或下线时只吊销它自己，而不影响其他客户端。共享单一 token 会让任何一次吊销变成全站事故，也无法在审计中区分"哪个客户端做了什么"。

本规格定义每客户端独立 token 的完整生命周期：创建、轮换、吊销、鉴权与审计。核心安全要求是：服务端只存 token **摘要**，完整明文只在创建与轮换响应中出现一次；API、日志、UI 与审计一律脱敏。

使用者是管理员（Web 与管理 API）与 `jrpc`（持有自己的 token 访问服务端下发通道）。属于 P1 阶段。REST 契约见 `docs/API.md` §4.3 与 §1.4，安全要求见根 `SECURITY.md`，存储真源见 ADR-0004，本规格不重复其正文。

## 2. 需求

- 每个客户端持有自己的 token；不同客户端的 token 不得相同、不得互用、不得跨客户端授权。
- token 生命周期动作：创建（随客户端一起或单独发行 enrollment 凭据后产出）、轮换、吊销。
- 服务端只持久化 token 摘要，不持久化可用于直接鉴权的明文；鉴权时用恒定时间比较摘要。
- 完整 token 只在创建或轮换响应中出现一次；后续读取接口、列表接口与 UI 只返回掩码与元数据。
- 轮换使旧 token 在明确边界后立即失效，新 token 生效；轮换不得影响其他客户端。
- 吊销使该 token 的后续鉴权失败；**已吊销是终态，不提供恢复路径**——既不能 un-revoke，也不能靠重新发行凭据绕过（对已吊销客户端发行凭据返回 409）。需要恢复时新建客户端。
- token 授权范围严格限定为当前客户端的 desired state、回执与运行状态；不得访问其他客户端，也不得访问管理员能力。
- token 管理动作（创建、轮换、吊销）与鉴权失败必须进入审计，且审计不记录完整 token（允许记录摘要前缀）。
- API、日志、UI、问题详情、指标与服务注册信息均不得出现完整 token。
- 服务注册、unit 与进程命令行不得包含 token；`jrpc` 的凭据经其本地 SQLite 或受限输入提供，不作为命令行普通参数。

- 范围内：
  - 每客户端独立 token 的发行、轮换、吊销与鉴权。
  - 摘要存储、掩码展示与脱敏约束。
  - enrollment 凭据与正式 token 的关系与一次性语义。
  - token 相关的审计事件。
  - token 在服务注册与进程命令行的最小权限约束。
- 范围外：
  - **配置文件作为配置真源**：已被 ADR-0004 拒绝；不得提供从配置文件读取 token 或导出含明文 token 文件的路径。
  - 共享 token、全局 token 或跨客户端 token。
  - 多管理员、租户、RBAC、角色化的 token 权限粒度（P3）。
  - OIDC、外部身份提供者颁发的令牌与联邦凭据（P3）。
  - 管理员侧的 API key、脚本用长期令牌或 Web 个人令牌。
  - token 自动过期轮换策略引擎、IP 白名单绑定与速率配额等企业策略（P3）。
  - 新增 CLI 管理命令：token 动作只经管理 API 与 Web。

## 3. 设计

### 3.1 模块与依赖方向

token 的管理、摘要存储与鉴权全部位于 `jrps` 外壳；`jrpc` 侧只保存自己的 token 并在管理通道请求中携带。Core 不参与 token 鉴权，也不知道 token 的存在。客户端与 token 摘要是外壳私有的 GORM 模型。

### 3.2 token 生命周期

```text
创建客户端 / 发行 enrollment 凭据
   │
   ▼
jrpc 用 enrollment 凭据 ──▶ POST /agent/v1/enrollments
   │                          └──▶ 换取客户端身份 + 独立 token（明文仅此一次）
   │
   ├──▶ 轮换：生成新摘要，旧摘要在明确边界后失效，响应返回新明文一次
   │
   └──▶ 吊销：摘要标记为失效，后续鉴权一律 401
```

- token 由服务端生成的随机值构成，具备足够熵；不使用可猜测的自增或派生序列。
- 服务端保存摘要；鉴权时对请求携带值计算摘要并与存储摘要做恒定时间比较。
- 轮换是原子写入：新摘要与旧摘要失效标记在同一事务提交，避免中间态同时拒绝新旧 token。
- enrollment 凭据是一次性或短期的：使用后立即失效或过期；对已绑定客户端重复 enrollment 被拒绝，需要管理员重新发行凭据。
- 已吊销或已轮换失效的 token 在鉴权失败时返回统一的 401 问题详情，不区分具体原因以免信息泄漏。

### 3.3 脱敏约束

| 位置 | 要求 |
|---|---|
| 创建/轮换响应 | 允许返回一次完整 token，UI 将其标记为一次性展示 |
| 列表与详情接口 | 只返回掩码（不足以还原完整值）与元数据 |
| 日志 | 只记录客户端 ID 与摘要短前缀，禁止记录完整值 |
| UI | 只在创建或轮换成功时展示一次完整 token，历史列表只展示掩码与元数据 |
| 审计事件 | 记录主体、动作、对象客户端与结果，不含完整 token |
| 指标 | 不得包含 token、Authorization 或 Cookie |
| 服务注册/unit/命令行 | 不得包含 token |

### 3.4 鉴权与隔离

- 客户端 token 只在 `/agent/v1` 管理通道生效，不能登录管理 API，也不能换取管理员会话。
- 每次鉴权必须校验 token 所属客户端身份；请求的 revision 与回执对象必须属于同一客户端，越权访问返回稳定问题码，不泄露其他客户端的存在性。
- enrollment 使用一次性凭据而非客户端 token；两者不得互相替代。
- 鉴权失败计入审计并对日志做限流，避免爆破面与日志刷屏。

### 3.5 与其它功能的关系

- 客户端实体与 token 摘要的持久化形态见 FR-09 规格。
- token 是 FR-08 enrollment 与 desired state 获取的鉴权基础。
- Web 上的 token 操作界面与一次性展示交互见 FR-11 规格。

## 5. 验收标准

- 自动化：两个客户端各自持有不同 token；互换 token 访问对方 desired state 被拒绝且响应不泄露对方存在性。
- 自动化：持久化记录中不存在可用于直接鉴权的 token 明文，只存在摘要。
- 自动化：轮换后旧 token 立即鉴权失败、新 token 成功；轮换不影响其他客户端。
- 自动化：吊销后该 token 的所有管理通道请求返回 401；已吊销状态不可恢复。
- 自动化：列表与详情接口、UI 数据、日志、指标与审计事件中均不含完整 token。
- 自动化：enrollment 凭据重复使用被拒绝；对已绑定客户端重复 enrollment 被拒绝，需管理员重新发行。
- 自动化：客户端 token 无法用于登录管理 API 或访问任何管理员端点。
- 自动化：创建、轮换、吊销均产生审计事件，且审计不含完整 token。
- 自动化（随 FR-08 补验）：鉴权失败产生审计事件。鉴权的唯一挂载点是 `/agent/v1` 的受保护端点（desired-state、apply-results、connect），它们随 FR-08 交付；当前该通道只有公开的兑换端点，鉴权失败审计没有可挂载处，因此不随本批标记通过。
- 自动化：Linux unit 与 Windows 服务注册内容、进程命令行均不含 token。
- 边界：超长或含非 UTF-8 字符的 token 输入、缺失 Authorization 头、并发轮换同一客户端、并发 enrollment 均有确定行为与中文安全提示。
- 实机（需用户确认）：在一台机器上创建两个客户端，分别为其启动一个 jrpc 并完成 enrollment；在 Web 中对其中一个执行轮换，确认该 jrpc 重连失败而另一个继续正常；再对第二个执行吊销，确认其重连失败、审计列表出现对应条目、页面中只见掩码。

## 6. 风险与待定

- **风险**：token 明文可能被误写入 SQLite 或日志之外的介质。缓解方式是存储层只暴露摘要字段，写入路径与脱敏检查由单测覆盖。
- **风险**：轮换后正在重连的 jrpc 会短暂失败，若客户端未实现退避可能产生连接风暴。缓解方式在 FR-08 的重连策略中处理。
- **风险**：凭证明文静态存储是已接受风险，文档与 UI 不得声称加密。
- **待定**：摘要算法与比较实现优先复用项目已有的标准库能力，不引入新依赖；如需新增依赖须先申请批准。
- **已定**：本 FR 交付凭据的发行、兑换、轮换、吊销与鉴权，以及两组路由；`/agent/v1` 的 desired-state、apply-results 与 connect 三个端点归 FR-08。FR-08 规格把「enrollment 全流程」列在自己范围内，此处按「凭据生命周期归 FR-07、身份建立后的配置下发归 FR-08」切分，两侧不重复实现。
- **已定**：enrollment 凭据有效期默认 **1 小时**。凭据是一次性短凭据，有效期过长会放大泄漏窗口，过短会让首次部署反复失败；该值随后续 Web 交互可调，调整不影响一次性语义。
