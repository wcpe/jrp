# 功能规格：TCP、UDP、HTTP、HTTPS 四种代理

> 状态：草拟 · 关联 PRD：FR-06a · 分支：feature/proxy-basic-types

## 1. 背景与目标

FR-06a 要求 Core 支持 TCP、UDP、HTTP、HTTPS 四种代理模式。这四种是绝大多数部署场景的主力形态，也是官方 frpc 互操作矩阵中被访问最频繁的一组。它们的转发语义差异很大：TCP 是按端口的一对一透传，UDP 是无连接数据报的会话化管理，HTTP 是按主机名与路径的多路复用路由，HTTPS 在 P1 则是**不终止 TLS 的透传**。

本规格解决的具体问题是：把这四种差异明显的转发语义统一到一套代理生命周期与路由模型之下，同时明确每种代理「能看到什么、不能看到什么」的能力边界，尤其是 HTTPS 透传场景下不得声称可采集正文。使用者：Core 代理层、jrps 装配层、管理员与被代理服务。所属阶段：P1。

## 2. 需求

- 支持 TCP 代理：按服务端端口接收连接，转发到客户端侧被代理服务的目标地址。
- 支持 UDP 代理：按服务端端口接收数据报，以会话化的方式转发到客户端侧目标，并在空闲后回收会话。
- 支持 HTTP 代理：按主机名、路径与 P1 已支持的其他路由参数选择目标，支持多代理共享同一入口端口。
- 支持 HTTPS 代理：P1 为 TLS 透传，不终止 TLS、不解密、不采集正文。
- 四种代理共用同一套生命周期：注册校验 → 资源创建 → 接收流量 → 停止接收新流量 → 排空活动连接。
- 代理注册必须校验字段、权限、端口/域名冲突与 P1 范围；失败不留下半注册监听器或路由。
- 代理层不依赖 SQLite、管理 API、Web 或通知；采集能力属于 jrps 适配器，不进入协议消息或 Core。
- 传输层与代理层解耦：四种代理都必须能在 FR-05a / FR-05b / FR-05c 全部传输之上工作。

- 范围内：四种代理的路由语义、生命周期、注册校验、并发与资源约束、HTTP 采集开关的挂载点、HTTPS 透传的能力边界声明。
- 范围外：
  - **「JRP 客户端连接官方 frps」这一反向兼容方向，本轮不做**，本规格不承载任何反向兼容承诺。
  - STCP 与 XTCP 代理（FR-06b）。
  - P2 的 SUDP 与 TCPMUX（FR-18）、剩余 HTTP 参数与插件能力（FR-19）。
  - **JRP 终止 TLS 后的 HTTPS 正文采集（FR-21，P2）**：P1 的 HTTPS 代理不做 TLS 终止，不解密，不生成正文记录。
  - 正文采集的存储与保留实现细节（FR-13）。
  - P3 的数据节点、节点 RPC、选举、分布式锁、共享数据库、租户、RBAC、OIDC。

## 3. 设计

### 3.1 统一生命周期与配置应用

四种代理共用同一套生命周期，与 `docs/ARCHITECTURE.md` §5.1 的无中断配置应用流程一致（ADR-0005）：

1. **准备**：校验代理定义，构造监听器、路由表项与依赖资源，不影响当前生效快照。
2. **健康检查**：验证端口绑定成功、路由可解析、必要依赖可达。
3. **原子发布**：一次性切换生效快照，新连接只使用新版本。
4. **排空**：旧资源停止接收新流量，已有流继续到自然结束或排空上限。

任一步在发布前失败都释放新资源并保留旧版本。停止接收新流量后，活动连接按生命周期排空，不强制切断。

### 3.2 注册校验顺序

代理注册按固定顺序校验，任一环节失败即返回明确错误：

1. 字段合法性：名称、类型、入口、目标地址、可选安全与限速参数。
2. 权限：该客户端是否被允许声明该入口与类型。
3. 冲突：服务端端口占用、HTTP 主机名与路径组合冲突。
4. P1 范围：不属于 P1 的参数或插件返回可判定的不支持错误，而不是部分应用。

成功响应只在资源可用后返回；失败不得留下半注册监听器或路由。

### 3.3 TCP 代理语义

- 入口：服务端独占端口。
- 路由：一个入口端口对应一个目标地址，无按内容的二次分发。
- 转发：用户连接到服务端端口后，服务端请求工作连接，绑定后进入双向透明转发。
- 生命周期：单条用户连接对应一条工作连接；任一侧关闭即开始排空另一侧。
- 约束：目标地址必须是该客户端已被允许的地址集合内的地址，不允许代理层任意转发到未声明目标。

### 3.4 UDP 代理语义

- 入口：服务端独占端口。
- 路由：同一入口端口按对端地址识别会话，同一对端地址的数据报归属同一会话。
- 转发：数据报经控制通道或专用工作通道送达客户端，客户端转发到目标并返回响应。
- 会话管理：会话有空闲上限，超时后回收；会话数有上限，达到上限时新对端被拒绝并有可观测事件。
- 约束：数据报大小受上限约束，超过上限的数据报被丢弃并计数，不按声明长度无界分配。
- 差异：UDP 无连接语义，因此「连接关闭」对应「会话空闲回收」，上层不得用 TCP 的关闭语义推断 UDP 状态。

### 3.5 HTTP 代理语义

- 入口：可与其他 HTTP 代理共享同一服务端端口。
- 路由：按请求主机名、路径前缀及 P1 已支持的其他参数选择目标代理；无匹配时返回明确的未匹配响应，不回显内部路由表。
- 转发：请求经工作连接送达客户端侧目标服务，响应原路返回。
- 采集挂载点：HTTP 是**唯一**允许开启正文采集的代理类型；采集开关逐代理配置，默认关闭。
- 采集边界：Core 只提供采集点，不实现存储；正文与元数据的落盘属于 jrps 适配器（`docs/PROTOCOL.md` §10）。关闭采集时数据面不得触发 SQLite 请求记录路径。

### 3.6 HTTPS 代理语义（P1 为透传）

**HTTPS 在 P1 是透传，不终止 TLS。** 由此产生三条硬边界：

1. **不解密**：Core 不持有、不配置、不协商被代理服务的 TLS 证书与私钥；TLS 握手发生在最终用户与被代理服务之间。
2. **不采集正文**：HTTPS 透传场景下 Core 无法看到明文 HTTP 语义，因此**不生成正文记录**，也不得在 UI、API 或文档中暗示可读取其正文。
3. **不按内容路由**：由于请求内容不可见，HTTPS 代理只能按入口端口路由，不能按主机名或路径分发（该能力依赖 P2 的 TLS 终止）。

- 入口：服务端独占端口（因无法按主机名分发）。
- 转发：透传字节流，Core 不解析、不修改、不缓冲完整请求。
- 未来演进：P2 若实现 JRP 明确终止 TLS 后的采集，必须新增 ADR 与规格，并建立证书治理（FR-21、`docs/PROTOCOL.md` §10）。

### 3.7 与传输的关系

代理层只依赖「连接」抽象，不感知底层是 TCP、WebSocket/WSS、KCP 还是 QUIC。四种代理与 FR-05a / FR-05b / FR-05c 全部传输的组合构成 `docs/PROTOCOL.md` §9 的互操作矩阵。传输差异（如 KCP 的丢包、QUIC 的迁移）由传输层吸收，代理层不做补偿。

### 3.8 与 ADR 的关系

- Core 模块边界与「Core 只承载数据面能力」遵循 ADR-0002 与 ADR-0003。
- 无中断配置应用遵循 ADR-0005。
- HTTP 正文采集的存储与保留策略遵循 ADR-0007。
- 兼容实现的独立性与固定基线遵循 ADR-0010（取代 ADR-0001），本规格不重复其决策正文。

## 5. 验收标准

正常路径：

- TCP 代理：用户连接服务端端口后数据双向可达，关闭一侧后另一侧排空。
- UDP 代理：同一对端地址的往返数据报正确送达，响应回到原对端。
- HTTP 代理：按主机名与路径正确路由到目标；多个代理共享同一入口端口时互不干扰。
- HTTPS 透传：TLS 握手在用户与被代理服务之间直接完成，数据双向可达。

HTTPS 透传边界（重点）：

- 断言 HTTPS 代理不生成任何正文记录：开启采集开关后，HTTPS 代理仍不产生正文分段。
- 断言 Core 不持有被代理服务的证书或私钥配置入口。
- 文档与 UI 口径一致：不声称 HTTPS 透传场景下可读取正文。

边界：

- HTTP 请求无匹配路由时返回明确响应，不回显内部路由表。
- UDP 数据报等于上限、上限加一、上限减一的行为分别为接受、丢弃并计数、接受。
- UDP 会话数达到上限时新对端被拒绝并有可观测事件。
- HTTP 采集开关关闭时，数据面不触发 SQLite 请求记录路径。

错误路径：

- 端口冲突、域名冲突、目标越权、字段非法、P1 范围外参数五类注册失败均返回明确错误，且无半注册监听器或路由残留。
- 工作连接建立失败时用户连接被明确关闭，不悬挂。
- 客户端离线时代理入口停止接收新流量，已有连接按排空上限处理。
- 关闭代理后 goroutine、监听器与连接计数归零。

实机：

- 四种代理在 FR-05a / FR-05b / FR-05c 传输上的组合需按互操作矩阵执行；涉及真实网络的组合（尤其 UDP 在 NAT 后的可达性）需用户在目标环境确认实机通过。
- 测试全绿不能替代真实网络验收。

## 6. 风险与待定

- **HTTPS 透传与用户预期冲突**：管理员可能期望在 HTTPS 上按域名路由或查看请求。P1 明确不支持，需要在 Web 与文档中前置说明，避免形成「看起来支持」的界面。
- **UDP 在 NAT 与防火墙下的可达性**：UDP 会话的空闲回收与中间设备的 NAT 映射超时可能不一致，需要用户在真实网络环境确认合适的空闲上限。
- **HTTP 路由匹配顺序未细化**：主机名与路径组合的优先级、最长前缀匹配与精确匹配的取舍需要在实现前定稿，并写入 `docs/PROTOCOL.md`。
- **采集挂载点形状需与 FR-13 对齐**：本规格只定义「Core 提供采集点、不实现存储」，具体接口形状需与 FR-13 规格协同，避免两处各写一套。
- **依赖传输完成度**：完整矩阵验收依赖 FR-05b 与 FR-05c 的依赖获批；在依赖获批前，矩阵中对应组合无法执行。
