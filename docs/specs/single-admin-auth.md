# 功能规格：单管理员认证

> 状态：草拟 · 关联 PRD：FR-02 · 分支：feature/single-admin-auth

## 1. 背景与目标

JRP P1 面向个人与小团队的单机部署，管理入口只需要一个管理员。与此同时，管理 API 一旦暴露到不可信网络就会成为最高价值目标，因此初始化、会话和 CSRF 必须一次做对，而不是留给后续阶段补齐。

本规格定义两件事：

1. **首次初始化**：在本机以 `jrps init` 建立唯一管理员凭据，且该路径永久一次性。
2. **单管理员 Web 会话**：安全 Cookie 会话 + CSRF 状态，覆盖登录、查询、登出与失效。

使用者是部署 `jrps` 的管理员。属于 P1 阶段。管理 API 契约见 `docs/API.md` §4.1 与 §4.2，本规格只定义行为与验收、不改写契约；存储真源见 ADR-0004，边界见 ADR-0003，本规格不重复其正文。

## 2. 需求

### 2.1 首次初始化

- 唯一入口是本机 CLI `jrps init`；P1 不提供远程 HTTP 初始化端点，也不提供 Web 初始化页面。
- 只允许在目标 SQLite 尚无管理员记录时执行；成功后该初始化路径永久关闭。
- 默认通过交互式标准输入读取管理员密码，**禁止把密码放入普通命令参数**；自动化方式使用受限标准输入或一次性环境变量，且环境变量不得写入日志或 unit。
- 数据库迁移、管理员创建与初始化完成标记必须在同一事务中提交；失败不得留下可登录的半初始化状态。
- 已完成初始化时重复执行返回明确中文错误，不得重置管理员、覆盖密码或绕过现有会话安全策略。
- 初始化发生在本机 CLI，不建立浏览器会话，因此不适用 Web CSRF；首次成功登录后所有修改请求仍按 CSRF 执行。
- 初始化完成前，管理 API 除 `/healthz` 与 `/readyz` 外返回 503，避免未初始化状态被远程利用。

### 2.2 会话与 CSRF

- 登录成功后建立 `HttpOnly`、`Secure` 与合理 `SameSite` 属性的 Cookie 会话；Web 生产部署使用 HTTPS，明文管理连接不作为生产形态。
- 会话可注销，注销后会话标识立即失效；服务端不保留可重放的会话密钥明文。
- 所有修改状态的管理请求必须验证 CSRF token；只读 GET 不产生副作用。
- 会话查询接口只返回脱敏信息与 CSRF 协议所需状态，不返回密码、密码派生材料、完整 Cookie 或服务端会话密钥。
- 登录失败使用统一的问题详情与中文提示，不区分"用户不存在"与"密码错误"。
- 登录、登出与失败尝试进入审计事件，审计不记录密码或凭据材料。

### 2.3 引导参数

- 管理 API 根监听是三项引导参数之一，变更需要重启；它不得通过热更流程变更。
- 数据目录与 SQLite 路径同样是引导参数，影响管理员记录的存放位置。

- 范围内：
  - `jrps init` 的一次性初始化与事务原子性。
  - 单管理员登录、会话查询与登出。
  - 安全 Cookie 属性与 CSRF 校验。
  - 初始化完成前的 API 就绪边界。
  - 登录相关的审计与脱敏。
- 范围外：
  - **配置文件作为配置真源**：已被 ADR-0004 拒绝；管理员凭据与初始化状态只存 SQLite，不支持配置文件声明管理员或配置文件导入导出。
  - 多管理员、多租户、角色、权限组与 RBAC（P3）。
  - OIDC、SAML、LDAP、外部身份提供者与联合登录（P3）。
  - 自助密码找回、邮箱验证、二次因子与 WebAuthn。
  - 新增除 `jrps init` 之外的 CLI 管理命令（属 FR-29 的服务生命周期命令不在本范围）。
  - API key、长期个人令牌或供脚本使用的非 Cookie 凭据（P1 只支持浏览器会话）。
  - 会话多点并发限制、异地登录检测与风控。

## 3. 设计

### 3.1 模块与依赖方向

认证与会话能力全部位于 `jrps` 外壳：CLI 子命令负责初始化，管理 HTTP 层负责会话与 CSRF。Core 不参与认证，也不知道管理员、会话或 CSRF 的存在。会话与管理员模型是外壳私有的 GORM 模型，不进入 Core。

### 3.2 初始化状态机

```text
启动 jrps ──▶ 读取初始化标记
              ├─ 未初始化：管理 API 除健康检查外返回 503，等待 jrps init
              └─ 已初始化：正常提供 /api/v1 与 Web

jrps init ──▶ 校验尚无管理员记录
              ├─ 已有：返回中文错误并退出，不做任何修改
              └─ 无：读密码 → 派生材料 → 同一事务写入管理员 + 初始化标记 → 成功
```

- 密码只经标准输入或一次性环境变量读取，读完后在内存中按最小生存期处理，不写入日志、不写入命令行可见参数。
- 凭据材料按已接受风险明文静态存储于 SQLite（ADR-0004），但不得声称已加密；派生参数与盐随记录保存。
- 初始化标记与管理员记录同事务提交；事务失败时整体回滚，进程下次启动仍处于未初始化状态。

### 3.3 会话与 CSRF 流程

- `POST /api/v1/session`：校验凭据，通过后建立会话并返回会话脱敏信息与 CSRF 状态；失败返回统一问题详情。
- `GET /api/v1/session`：返回当前会话脱敏信息与 CSRF 协议所需状态。
- `DELETE /api/v1/session`：注销当前会话并使其立即失效。
- 修改类请求（POST、PATCH、DELETE 及任何产生副作用的动作）必须携带并校验 CSRF token；校验失败返回 403 且不产生副作用。
- 只读 GET 不要求 CSRF token，但也不得产生副作用。
- 会话过期后请求返回 401，Web 侧应引导重新登录而非静默重试。

### 3.4 安全边界

- 数据目录、SQLite、备份介质与宿主机是信任边界；浏览器与网络输入不可信。
- 所有输入限制长度与字符集，登录尝试有速率约束，避免凭据爆破。
- 问题详情对外只暴露稳定问题码与中文摘要，不含堆栈、文件路径或 SQL。
- 日志与审计包含主体与时间，但不包含密码、Cookie 或会话密钥。
- 服务注册、unit 与进程命令行不得包含管理员密码或任何凭据。

## 4. 任务拆分

- [ ] 先写失败测试：未初始化时管理 API 返回 503；重复 init 被拒绝且不覆盖密码；缺少或错误 CSRF token 的修改请求返回 403 且无副作用。
- [ ] 实现 `jrps init` 的密码读取、事务初始化与一次性标记。
- [ ] 实现管理员记录的凭据派生与存储，确认不在日志或命令行暴露。
- [ ] 实现会话建立、查询与注销端点及脱敏响应。
- [ ] 实现安全 Cookie 属性与 CSRF token 发放与校验中间件。
- [ ] 实现登录速率约束与统一失败提示。
- [ ] 实现登录、登出与失败尝试的审计事件。
- [ ] 实现初始化前的就绪边界，健康检查保持可用。
- [ ] 补齐管理监听作为引导参数的说明与重启标注。
- [ ] 运行 jrps 测试、静态检查与构建；同步 PRD、ARCHITECTURE、API、OPERATIONS、SECURITY、CHANGELOG 中受影响内容。

## 5. 验收标准

- 自动化：全新数据目录启动后，`/healthz` 与 `/readyz` 可用，其余 `/api/v1` 端点返回 503。
- 自动化：执行 `jrps init` 并输入密码后初始化成功；再次执行返回明确中文错误，管理员记录与密码未被覆盖，已有会话安全策略未被绕过。
- 自动化：初始化事务失败（例如磁盘写入失败或进程中断）后重启仍处于未初始化状态，不存在可登录的半初始化状态。
- 自动化：登录成功后响应体不含密码、派生材料、完整 Cookie 或服务端会话密钥；会话查询只返回脱敏信息与 CSRF 状态。
- 自动化：携带有效 CSRF token 的修改请求成功；缺失或错误 token 返回 403 且不产生副作用；只读 GET 不产生副作用。
- 自动化：登出后使用原会话访问管理端点返回 401。
- 自动化：登录失败响应不区分用户不存在与密码错误；连续失败达到阈值后被限流。
- 自动化：登录、登出与失败尝试均产生审计事件，审计内容不含密码或凭据材料。
- 自动化：`jrps init` 不接受把密码作为普通命令参数传入的调用形态；进程命令行与日志中不含密码。
- 边界：超长密码、空密码、非 UTF-8 输入、并发重复 init 均有确定行为与中文提示。
- 实机（需用户确认）：在 Windows 与 Linux 上各执行一次完整流程——启动 jrps、执行 `jrps init`、在浏览器中用 HTTPS 访问管理台登录、执行一次修改操作验证 CSRF、登出后确认会话失效；确认 Cookie 具备 `HttpOnly`、`Secure` 与 `SameSite` 属性（浏览器开发者工具核对）。
  - **执行记录（2026-09-20）**：Windows 侧由真实 Chromium 经 HTTPS 走通未登录跳转、登录、会话 Cookie 属性核对、通知目标创建与删除、缺少 CSRF 的修改被拒（403）、登出后受保护端点返回 401，共 12 项全通过；Linux 侧在容器内执行 `jrps init` 与 HTTPS 监听，由容器内探针完成同等断言，共 10 项全通过。Cookie 实测属性为 `Path=/api; HttpOnly; Secure; SameSite=Strict`。
  - **环境限制**：本次执行环境的主机到容器端口转发不可用，Linux 侧无法由主机浏览器访问容器内的管理台，容器内也没有图形浏览器，因此 Linux 侧未做浏览器交互取证——浏览器交互路径由 Windows 侧覆盖。本次记录不构成"Linux 侧也完成浏览器取证"的声明。

## 6. 风险与待定

- **风险**：管理员密码遗忘后 P1 没有自助找回路径，只能通过重新初始化（需要清空或重建数据目录）恢复，代价较高。缓解方式是在运维文档中明确提示保存恢复材料。
- **风险**：`Secure` Cookie 在自签名或本地 HTTP 开发场景下会导致登录不可用。这是生产安全要求，开发态需使用明确的本地回退而非削弱生产默认值。
- **风险**：凭据明文静态存储是已接受风险，一旦数据目录或备份泄露即暴露；文档与 UI 不得声称加密。
- **待定**：登录速率约束的具体阈值与锁定时长需在实现前定稿，暂按有界限流实现。
- **待定**：会话空闲过期与绝对过期时长的默认值需要在 Web 交互确认后写入本文档，避免管理员频繁掉线。
- **已定**：管理面 TLS 终止由 jrps 内建承担（`--tls-cert` 与 `--tls-key`，两者必须成对提供，缺一个即按启动失败处理而不静默降级为明文；启动日志打印证书 SHA-256 指纹供自签场景核对）。选择内建而非部署层反向代理，是为了让 §5 的"在浏览器中用 HTTPS 访问管理台"在单机部署下即可成立；反向代理仍是可选叠加，不作为前置条件。
- **待定**：反向代理部署形态下的证书链与信任传递（客户端证书、上游 `X-Forwarded-*` 处理）尚未定义；内建 TLS 已可独立满足当前验收，该项在引入反向代理部署时再定稿。
