# 功能规格：安全审计与保留策略

> 状态：草拟 · 关联 PRD：FR-16 · 分支：feature/audit-and-retention

## 1. 背景与目标

P1 只有一个管理员，单管理员不等于不需要追责：一旦数据目录被异常访问、正文被批量查看或保留策略被放宽，管理员自己也需要一份无法事后篡改的记录来说明发生过什么。日志能解释故障，但会因容量和性能而降级丢弃，不能充当不可否认的证据。

FR-16 解决三件事：

1. 把"安全敏感操作必须留痕"落成明确的审计事件模型：主体、动作、对象、结果、时间、脱敏上下文。
2. 把正文保留策略（默认 30 天、总量 5 GiB，任一先到即清理）作为**受审计的策略对象**管理，而不是散落在采集代码里的常量。
3. 划清审计与日志的边界：审计是不可否认的操作记录，日志是诊断输出，两者不得互相替代。

使用者是管理员（经 Web 与 `GET /api/v1/audit-events`）与合规复核流程。属于 P1 阶段。审计范围见根 `SECURITY.md` §5，配置真源见 ADR-0004，正文存储分离见 ADR-0007，边界见 ADR-0003，本规格不重复其正文。

## 2. 需求

### 2.1 审计事件

- 审计事件至少包含六项：主体、动作、对象、结果、时间、脱敏上下文。
- 主体是唯一管理员或经认证的客户端；客户端只能产生属于自身的动作记录，不得代替管理员主体。
- 动作使用具名枚举，不得用自由文本拼接；动作集合在本规格内封闭管理。
- 对象是操作目标的类型与标识组合：客户端、代理、配置版本、token、通知目标、采集记录、保留策略、会话。
- 结果区分成功、失败与被拒绝三类；失败与被拒绝必须记录，不得以"没做成就不算操作"为由跳过。
- 时间是 RFC 3339 UTC 的事件发生时间，由服务端生成，不接受客户端提供的时间。
- 脱敏上下文只允许携带标识、类型、数量与安全错误摘要；**不得记录完整 token、密码、Cookie、Authorization、完整正文或分段文件路径**。
- 审计写入不得因容量或性能被丢弃：审计与日志的降级策略不同，审计必须完整落库。

### 2.2 必须审计的动作

按 SECURITY §5 的口径，以下动作必须产生审计事件：

- 登录、登出与登录失败尝试。
- 客户端 token 的创建、轮换与吊销。
- 配置变更：代理创建、修改、删除与 restore。
- 配置应用结果：每个阶段的成功与失败。
- 正文查看、导出与删除。
- 通知目标的创建、修改、删除与测试通知。
- 保留策略变更。
- 日志查询（按 FR-12 §3.5，只记录查询条件摘要与结果条数）。

正文查看、导出与删除**除会话与 CSRF 校验外还必须写审计**；仅凭会话不能构成访问证据。

### 2.3 保留策略

- 正文默认保留 **30 天**，正文总量上限 **5 GiB**；两个限制独立计算，**任一先到即触发清理**。
- 保留策略是受管理的策略对象：默认关闭采集、保留天数与总量上限均可经管理 API 变更，且每次变更必须审计。
- 策略变更走即时生效路径，不需要重启；变更不得追溯性地恢复已清理的正文。
- 策略值必须有边界校验：天数与总量为正数且有上下限；非法值返回 400 问题详情，不静默收敛。
- 清理执行结果（成功、部分成功、失败）与异常（孤儿段、缺失引用）必须可审计，不得静默处理。
- 审计记录本身不参与正文的 30 天与 5 GiB 清理，由独立的审计保留策略管理。

- 范围内：
  - 审计事件的六项字段模型与动作枚举。
  - §2.2 列出的必须审计动作清单及其写入点。
  - `GET /api/v1/audit-events` 的分页查询与过滤。
  - 正文保留策略（默认关闭、30 天、5 GiB）作为受审计策略对象的读写与边界校验。
  - 清理执行结果与异常处理动作的审计写入。
  - 审计与日志的边界定义。
  - 审计记录自身的保留策略与清理边界。
- 范围外：
  - **配置文件作为配置真源**：已被 ADR-0004 拒绝；审计事件与保留策略只存 SQLite 并经管理 API 变更，不支持审计配置文件或文件型审计输出。
  - 日志的等级、脱敏与落盘：属 FR-12。
  - 正文清理的具体执行路径、分段滚动与索引文件一致性：属 FR-13；本功能只负责策略对象与结果审计。
  - 审计与凭证的静态加密：项目不提供，不得声称。
  - 多管理员归因、租户维度审计、RBAC 决策日志与 OIDC 身份事件（P3）。
  - 审计导出为外部 SIEM 格式、远程审计 syslog、WORM 存储与防篡改签名链（P3）。
  - 审计事件的完整性证明、默克尔树与区块链式存证。
  - 数据节点汇聚审计与集中审计后端（P3）。

## 3. 设计

### 3.1 模块与依赖方向

- Core 侧：不参与审计。Core 不知道管理员、策略或审计表的存在，也不写入审计；配置应用与代理事件只经 FR-27 的有界事件通道回流到外壳。
- jrps 侧：持有审计写入服务、审计查询端点与保留策略对象。审计写入点分布在管理 API 层、配置编排层、采集访问层与通知管理层，统一调用同一审计入口，避免各层自行拼装字段。
- jrpc 侧：只在本客户端 SQLite 记录与自身相关的应用结果和本地敏感操作；不向服务端上报审计，也不从服务端拉取审计。
- 依赖方向：外壳 → Core 单向。审计写入不得反向让 Core 等待持久化完成。

### 3.2 审计事件模型

| 字段 | 内容 | 约束 |
|---|---|---|
| 主体 | 管理员标识或客户端标识及其类别 | P1 只有一个管理员；不引入角色或租户字段 |
| 动作 | 具名枚举（登录、登出、token 轮换、正文查看等） | 枚举封闭管理，不用自由文本 |
| 对象 | 对象类型与对象标识 | 只携带标识，不携带敏感属性值 |
| 结果 | 成功、失败、被拒绝 | 失败与被拒绝同样记录 |
| 时间 | RFC 3339 UTC，服务端生成 | 不接受客户端时间 |
| 脱敏上下文 | 数量、阶段、安全错误摘要、关联 request ID | 白名单字段；不含完整秘密与完整正文 |

安全约束：审计内容不记录完整 token、密码、Cookie、Authorization、完整正文与分段文件路径。token 相关动作只记录客户端标识与 token 摘要前缀。错误摘要必须是安全可公开文本，不含堆栈、文件路径、SQL 或内部地址。

### 3.3 写入点与事务边界

- 审计写入与业务结果在同一事务内提交：业务成功但审计写入失败时整体回滚，不留下"发生了但没有记录"的操作。
- 审计写入不得阻断业务成功路径以外的补偿：若审计写入失败导致业务回滚，必须记录 ERROR 日志并让调用方收到明确的中文错误。
- 正文查看类读取动作的审计在读取**之前**落库：先留痕再返回内容，避免读取失败时无痕。
- 审计写入本身不产生新的审计事件，避免递归。
- 审计写入不进入有界事件队列的降级路径：审计不允许丢弃。

### 3.4 保留策略对象

- 策略对象包含三个值：默认采集关闭标记、保留天数（默认 30）、正文总量上限字节（默认 5 GiB）。
- 读写入口为 `GET/PUT /api/v1/capture-policy`，需要管理员会话与 CSRF；变更写入审计事件，记录变更前后摘要值。本规格为该端点与策略值的唯一权威来源，FR-13 只负责按策略执行清理。
- 边界校验：天数与总量为正数且落在上下限内；非法值返回 400 问题详情，不静默收敛为默认值。
- 策略变更即时生效，不需要重启；已清理的正文不因策略放宽而恢复，界面须如实说明。
- 策略变更只影响此后产生的正文的保留截止时间计算基准；已有分段的截止时间按既定规则重算或保持，实现须在文档中明确，不得出现两种口径。
- 策略对象与 FR-13 的清理执行分工：本功能负责策略值的管理与审计，FR-13 负责按该策略执行清理、维护索引与文件一致性并上报清理结果；清理结果回写后由本功能产生审计事件。

### 3.5 审计与日志的边界

| 维度 | 审计（本功能） | 日志（FR-12） |
|---|---|---|
| 目的 | 不可否认的操作记录 | 诊断与排障输出 |
| 触发 | 安全敏感操作显式产生 | 状态变化、错误、降级自动产生 |
| 完整性 | 不允许因容量或性能丢弃 | 允许按等级降级与丢弃 |
| 保留 | 独立审计保留策略，不随正文清理 | 外壳轮转与保留策略 |
| 内容 | 主体、动作、对象、结果、时间、脱敏上下文 | 等级、组件、中文摘要、关联 ID |
| 查询 | 需管理员会话，按动作与对象过滤 | 需管理员会话，按等级与组件过滤 |

同一操作可以同时产生审计与日志，但不得互相替代：有日志不等于已审计，已审计也不要求一定有对应日志。诊断信息不得塞进审计上下文，操作归因也不得只靠日志反推。

### 3.6 审计查询与访问控制

- `GET /api/v1/audit-events` 需要管理员会话；未认证返回 401。只读 GET 不产生副作用，但查询本身按 FR-12 的同类规则处理为安全敏感读取。
- 支持按时间范围、动作、对象类型、结果与游标分页过滤；过滤参数做长度与格式校验，非法参数返回 400。
- 响应使用 UTF-8 JSON，时间使用 RFC 3339 UTC；响应体不得包含任何未脱敏字段。
- P1 不提供审计导出接口，也不提供审计删除接口：审计不可被管理员通过 API 抹除。

### 3.7 审计保留

- 审计记录独立于正文保留：正文清理不得连带删除审计事件。
- 审计保留按独立的审计保留策略执行；策略变更必须审计。
- 审计清理只按时间维度执行，不按大小维度；清理动作本身写入最终一条审计事件后执行，并留下可查询的记录。

## 5. 验收标准

正常路径：

- 自动化：登录、登出、token 轮换、代理修改、配置应用成功、正文查看、通知目标变更、保留策略变更各自产生一条审计事件，六项字段齐全。
- 自动化：审计事件的时间由服务端生成且与客户端提交的时间无关；并发写入按发生顺序可读。
- 自动化：已登录管理员可按时间、动作、对象类型与结果过滤查询，响应为脱敏 JSON 且支持游标分页。

边界：

- 自动化：保留天数设为极小值与总量设为极小值时，两个限制各自独立触发清理，先到者生效；清理结果写入审计。
- 自动化：策略值为零、负数、超上限或非法类型时返回 400 问题详情，不静默收敛为默认值，且不写入部分变更。
- 自动化：策略放宽后已清理的正文不恢复，界面与 API 均如实说明。
- 自动化：审计查询的空结果集、分页末页与超长过滤参数均有确定行为与中文提示。
- 自动化：审计清理只按时间维度执行，执行后仍保留动作本身的可查询记录。

错误路径：

- 自动化：正文查看、导出与删除在返回内容之前已落审计；读取失败时审计仍存在。
- 自动化：业务事务提交但审计写入失败时整体回滚，不留下"发生了但没有记录"的操作，并记录 ERROR 日志。
- 自动化：审计内容中不含完整 token、密码、Cookie、Authorization、完整正文或分段文件路径；对这六类值逐一构造用例断言。
- 自动化：正文清理产生的孤儿段回收与缺失引用标记动作均写入审计，不静默处理。
- 自动化：正文被清理后对应的审计事件仍然存在，不因正文清理被删除。
- 自动化：未认证访问审计端点返回 401；API 不提供审计删除或审计导出接口。
- 自动化：审计写入不产生递归审计事件；`-race` 下并发审计写入无竞态报告。

实机（需用户确认，S2 批次）：在一台机器上启动 jrps，登录管理台；读取保留策略的默认值，确认采集默认关闭与两项保留天数；提交一次越界策略确认返回 400 且一次给出全部违规项，提交一次缺少 CSRF 的写入确认 403；变更一次保留策略并读回，随后在审计列表中确认该变更留有记录、内容为中文、包含变更前后值，且审计内容不含完整 token、密码、Cookie、Authorization 或正文。

实机（需用户确认，随 FR-13 补验）：开启采集并发起请求、查看一次正文、删除该条采集记录，确认正文查看与删除在返回内容之前已留审计；把保留时间与总量分别设为极小值，确认两个限制各自独立触发清理、先到者生效，且正文分段被回收后相关审计记录仍在。

实机（需用户确认，token 相关）：**已通过**。创建客户端、发行凭据、客户端兑换、轮换 token 与吊销 token 各有独立的审计动作（`client_create`、`client_credential_issue`、`client_enroll`、`client_rotate`、`client_revoke`），其中 `client_rotate` 与 `client_revoke` 是登记已久后首次有了写入点；审计不含 token 明文或摘要。

凭据发行与兑换单独成动作而非复用 `client_create` 与 `client_rotate`：动作名要能直接回答"发生了什么"，而"发了张可入场的凭据"与"建了个客户端"、"客户端首次注册领取 token"与"管理员主动轮换"在风险含义上完全不同，复用会让审计列表失去追溯力。

实机（需用户确认，随 FR-10 补验）：修改代理并应用，确认该动作产生一条审计事件。

实机（需用户确认，随 FR-11 补验）：在 Web 中查看审计列表，确认上述动作均可在界面查询。

上述后三条不随 S2 批次标记通过，待对应 FR 交付后一并验收。

**未接线项（需在补验前解决）**：`store.CleanupAuditEvents` 在生产路径中没有调用方——jrps 启动流程只装配了通知发送循环，审计清理没有后台触发点，因此"把保留时间设为极小值触发清理"当前无法在整机形态下执行。该项属本功能自身职责（规格 §3 把审计的保留与清理边界列入范围内），补触发点时需同时确认单轮删除上限与写事务占用时长的关系。

## 6. 风险与待定

- **风险**：审计写入与业务同事务会让审计故障直接变成业务失败。这是刻意取舍——宁可操作失败也不能留下无痕操作；需在运维文档中说明该失败模式与处置方式。
- **风险**：审计记录长期增长会占用 SQLite 空间。缓解方式是独立时间维度保留策略与清理动作留痕，并在 FR-14 观察审计表水位。
- **风险**：脱敏上下文若被后续需求随意扩字段，可能逐渐带入敏感值。缓解方式是字段白名单与针对六类敏感值的持续断言。
- **风险**：策略变更前后口径不一致会导致保留截止时间出现两种算法。缓解方式是变更语义在本规格内定死，并在界面与文档中一致表述。
