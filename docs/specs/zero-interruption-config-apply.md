# 功能规格：无中断配置应用

> 状态：草拟 · 关联 PRD：FR-10 · 分支：feature/zero-interruption-config-apply

## 1. 背景与目标

管理员修改代理配置是最高频的运维动作。若通过重启进程或先关旧监听再起新监听来生效，会切断已有代理连接，也会让一次配置错误直接放大为服务不可用。JRP 需要让绝大多数配置更新对活动连接透明，同时让失败和回滚语义清晰可验证。

本规格定义 `jrps` 与 `jrpc` 共用的单一配置应用状态机：`prepare → health-check → atomic publish → drain`。它把配置错误隔离在 active 路径之外，让新连接只看到完整的新版本，让已有流有机会自然结束，并在任何 publish 前失败时保留旧的 active 与 last-good。

使用者是管理员（经 Web 或管理 API 触发）与 `jrpc`（在下发到本客户端的新 desired revision 时自动触发）。属于 P1 阶段。状态机裁定见 ADR-0005，控制面与数据面边界见 ADR-0003，配置真源见 ADR-0004，本规格不重复其正文。

## 2. 需求

- 配置应用固定四个阶段，顺序不可跳过、不可合并：prepare、health-check、atomic publish、drain。
- prepare 阶段校验 revision 并构造新监听器、会话、路由与依赖资源，期间不得关闭或修改 active 资源。
- health-check 阶段验证新资源可用：端口绑定成功、必要依赖可达、快照参数在 Core 侧校验通过。
- publish 阶段一次性把 active 指针切换到新不可变快照；切换后新连接只使用新版本，不存在中间态。
- drain 阶段让旧资源停止接收新流量，已有连接与活动流继续到自然结束或排空上限，到上限后按既定策略强制关闭并记录。
- publish 之前的任一步失败：释放已准备的新资源，保留旧 active 与 last-good，写入 apply result 与审计事件。
- publish 之后的 drain 异常：进入告警、审计与有限重试路径，**不回切已被新连接使用的版本**；只有管理员经正式回滚流程创建并应用新的 desired revision 才会改变 active。
- 配置应用必须支持并发保护：同一实例的多个 Apply 不得同时进行指针切换，后到的请求必须排队或返回明确冲突。
- 只有三项引导参数变更需要重启：数据目录、SQLite 路径、管理 API 根监听。**其他 P1 配置不得以自动重启冒充热更**，也不得为实现方便而引入"修改后重启"的旁路。
- 回滚只能走"从历史版本内容创建新的 desired revision → 同一状态机"的路径，不得修改历史版本内容或直接篡改 active。
- `jrps` 与 `jrpc` 使用同一套阶段语义与阶段命名，以便两者回执可比、故障可对照。
- 每个阶段的进入、成功与失败都要产生 apply result 与审计事件，错误信息必须是安全可公开的中文摘要，不含堆栈、文件路径或 SQL。

- 范围内：
  - 四阶段状态机及其失败、回滚、并发、超时语义。
  - new-old 双资源的准备、切换与释放生命周期。
  - drain 上限、告警与不回切规则。
  - jrps 侧管理员触发的应用流程与 API 受理语义。
  - jrpc 侧由 desired revision 变化驱动的应用流程与回执。
  - 三项引导参数的重启例外认定。
- 范围外：
  - **配置文件作为配置真源**：已被 ADR-0004 拒绝；本功能不包括文件热加载、文件监听或以文件为触发源的重载路径。
  - 新增 CLI 管理命令：应用动作只经 `POST /api/v1/config-revisions/{revision}:apply` 与 Web 触发。
  - 配置文件的导入导出与 Web 批量/模板操作。
  - 多版本并存灰度、按百分比或按客户端分组的分批发布。
  - 传输层本身的实现细节与协议兼容行为（属 FR-04、FR-05a/05b/05c、FR-06a/06b）。
  - 数据节点间的配置分发、调度与故障转移。
  - 以自动重启守护进程代替热更的任何手段。

## 3. 设计

### 3.1 总体边界

外壳持有应用编排职责：从 SQLite 读取 desired revision 内容（ADR-0004），经 Core 提供的配置构建与校验入口得到不可变快照，再按状态机驱动 Core 的应用端口。Core 不读取数据库，只接受快照并返回应用结果与事件；外壳负责持久化 apply result、审计与告警。

`jrps` 与 `jrpc` 各有一份编排实现，两者阶段语义相同、输入不同：`jrps` 的输入是本地管理员变更，`jrpc` 的输入是服务端下发的 desired state（FR-08）。两侧不共享编排代码，而是通过一致的阶段命名与回执结构保证可对照。

### 3.2 状态机

```text
desired 变更
   │
   ▼
prepare ──失败──▶ 释放新资源 · 保留 active/last-good · 写失败结果
   │ 成功
   ▼
health-check ──失败──▶ 释放新资源 · 保留 active/last-good · 写失败结果
   │ 成功
   ▼
atomic publish（一次切换指针，不可部分成功）
   │ 成功：推进 last-good、记录 active
   ▼
drain（旧资源不再接新流量，已有流跑到自然结束或排空上限）
   │ 超时/异常：告警 + 审计 + 到上限强制释放，不回切
   ▼
完成
```

阶段迁移约束：

- prepare 未成功不得进入 health-check；health-check 未全部通过不得 publish。
- publish 是不可分割动作：快照路由表整体替换，不允许逐条替换形成半更新。
- drain 开始前旧资源已不再接收新连接；drain 期间旧资源只服务已有连接。
- 任一步失败都必须释放本轮已分配的新资源，不得留下悬挂监听器或 goroutine。

### 3.3 并发、超时与幂等

- 同一实例使用单一应用互斥：新的 Apply 在既有流程未终结前进入等待队列，或在超过等待阈值后返回 409 和明确的冲突问题码，由调用方重新读取 revision 后重试。
- **排队由外壳在 Core 之外实现**：Core 的 Apply（FR-26）在同一 Engine 并发时直接返回 `ErrApplyInProgress`，不排队、不静默合并。外壳据此决定是排队后串行调用，还是向调用方返回 409；两层职责不得混淆。
- 应用请求接受 `Idempotency-Key`；同一 revision 与同一键重复提交只触发一次真实流程，后续返回同一受理结果。
- 触发时基于的 revision 已过期（存在更新的 desired）返回 409，不允许最后写入静默覆盖；语义非法返回 422；受理成功可返回 202，最终结果通过资源状态与 SSE 事件观察。
- prepare、health-check、drain 各有明确超时；超时按阶段失败处理。drain 超时属于 publish 后异常，进入告警而不得触发回切。

### 3.4 失败保留与回滚

- publish 前失败：旧 active 指针不变，last-good 不变，新资源全部释放，失败原因写入 apply result 并审计。
- publish 后到 drain 结束前发生异常：只做告警、审计与有限重试；若强制释放旧资源，需要记录被强制关闭的连接数用于排障。
- 回滚：管理员读取历史版本内容，`jrps` 以其创建新的 desired revision，再走同一状态机。`jrpc` 侧回滚同样由服务端下发新的 desired revision，不由客户端自行翻回旧版本。
- 历史版本不得被修改或删除性改写；restore 只读取内容。

### 3.5 引导参数与"不得以重启冒充热更"

只有数据目录、SQLite 路径、管理 API 根监听三项变更需要重启，且必须在文档中明确标注为重启项。设计上堵死重启冒充热更的旁路：

- 应用流程不存在"停止旧进程后重启进入新配置"的分支，编排代码不具备重启进程的能力。
- 任何 P1 配置项变更都必须能映射到一次 prepare/publish 流程；若某配置项无法实现无中断切换，应先在本规格中登记为受限项并由用户确认处理方式，而不是退回重启。
- 监听器端口变化走 drain 路径处理：旧端口停接新连接，已在旧端口上的连接跑到 drain 上限；不得以"端口变了所以要重启"作为理由。

### 3.6 可观测与审计

- 每个阶段的开始、成功、失败、超时都要有中文日志，包含 revision、阶段、request ID，但不包含凭证或完整正文。
- apply result 记录阶段、成功状态与安全可公开的错误摘要，供 Web 与 API 展示。
- 配置应用事件经有界队列进入 SSE 与通知，慢消费者不得阻塞应用流程或数据面。

## 4. 任务拆分

- [ ] 先写失败测试：prepare 失败、health-check 失败、drain 超时三类场景下 active 与 last-good 应保持不变的断言；已建立的长连接在配置变更期间不得断开。
- [ ] 定义 revision 应用的结果模型与阶段枚举，落实三个 revision 的独立推进规则。
- [ ] 实现 prepare：构造新资源且不触碰 active。
- [ ] 实现 health-check：端口绑定、依赖可达与快照校验。
- [ ] 实现 atomic publish：一次性指针切换，过程中不出现半更新观察。
- [ ] 实现 drain：停接新流量、已有流自然结束、排空上限与强制释放。
- [ ] 实现 publish 后异常不回切的约束与告警审计路径。
- [ ] 实现并发互斥、等待队列、409 冲突与幂等键。
- [ ] 实现 restore：以历史内容创建新 desired revision 并复用同一状态机。
- [ ] 明确引导参数重启清单，并禁止任何以重启冒充热更的路径。
- [ ] 在 jrpc 侧接入同一阶段编排并回报 apply result。
- [ ] 运行 jrps、jrpc 测试、竞态检测与构建；同步 PRD、ARCHITECTURE、API、OPERATIONS、SECURITY、CHANGELOG 中受影响内容。

## 5. 验收标准

- 自动化：正常路径下修改一个 TCP 代理的目标地址并应用，四个阶段依次成功，active 与 last-good 均推进到新 revision；期间在旧快照上建立的长连接与在途数据流不中断。
- 自动化：prepare 失败（例如目标地址格式非法）时，active 与 last-good revision 不变，新资源全部释放，旧连接不受影响，返回 422。
- 自动化：health-check 失败（例如新端口被占用）时，同样保留旧版本，释放新资源，写入失败 apply result 与审计事件。
- 自动化：drain 期间已有长连接与在途流不中断；到达排空上限后被强制释放并记录连接数，且不回切 active。
- 自动化：并发 Apply 两个不同 revision 时，指针只按一次成型顺序切换，不存在双写；第二个请求要么排队串行、要么返回 409。
- 自动化：同一 `Idempotency-Key` 重复提交只执行一次真实流程并返回同一受理结果。
- 自动化：restore 历史版本后得到一个新的 revision，历史版本内容不变，走完四阶段后才成为 active。
- 自动化：三个引导参数变更被标记为需重启并写入文档；其余 P1 配置项变更均可映射到一次无中断应用流程，代码检索不存在重启旁路。
- 自动化：任一轮应用结束后不存在悬挂监听器、泄漏 goroutine 与未释放资源；资源释放计数器归零。
- 自动化：在 `-race` 下执行上述全部用例无竞态报告。
- 边界：空快照应用、仅删除代理的应用、端口从有到无与从无到有的切换、drain 上限取极小值的立即释放场景均有明确行为。
- 实机（需用户确认）：在一台机器上启动 jrps 与一个官方 frpc 或一个 jrpc，建立持续 TCP 长连接并持续收发数据；在 Web 中修改该代理配置并应用，确认传输全程无中断、无重连；随后故意提交一次被占用端口的变更触发 health-check 失败，确认已有连接继续可用且 last-good 未漂移。

## 6. 风险与待定

- **风险**：drain 上限设置过短会切断正常长业务流，过长会长期占用资源。缓解方式是默认上限在此规格交付前定稿，管理员可在 Web 查看当前排空状态，超限释放必须留审计记录。
- **风险**：health-check 无法覆盖所有运行期故障，例如依赖在 publish 后才不可达。该类故障归入 publish 后异常，只告警不回切，可能导致短时降级。
- **风险**：端口冲突型 health-check 失败在并发应用时可能与其他进程竞争，需要确保释放顺序与重试提示明确。
- **待定**：STCP 与 XTCP 等代理类型在 drain 阶段的自然结束判定标准需结合 FR-06b 的实现结果细化。
- **待定**：Web 上 active 与 last-good 的刷新频次与 SSE 事件粒度在 FR-11 中统一定义。
