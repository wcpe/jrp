# 功能规格：Webhook 与邮件通知

> 状态：草拟 · 关联 PRD：FR-15 · 分支：feature/notification-webhook-email

## 1. 背景与目标

管理员不可能一直盯着控制台，客户端掉线、配置应用失败或采集容量触顶都需要主动告知。但通知是典型的外部副作用：如果在业务事务内部直接发起远程调用，数据库回滚会留下已发出的通知，网络慢也会拖住管理事务。

FR-15 解决三件事：

1. 提供 Webhook 与邮件两种通知渠道，覆盖是与否两类必要触达。
2. 用**事务 outbox**把"记录待发送"与"真正发送"分开：业务事务提交成功后再触发外部副作用，**禁止事务内远程调用**。
3. 让失败可恢复：重试状态、退避、放弃与死信有明确设计，并且日志与 API 全程脱敏。

使用者是管理员（经 Web 通知页与 `/api/v1/notification-targets`）以及被通知的下游系统。属于 P1 阶段。outbox 与事务边界裁定见 ADR-0004 与 ADR-0003，运维排障口径见 OPERATIONS §5.6，本规格不重复其正文。

## 2. 需求

- 支持两种渠道：**Webhook**（向管理员配置的 URL 发送 HTTP 请求）与**邮件**（经 SMTP 发送）。P1 不提供其他渠道。
- 通知目标可增删改查；目标配置包含类型、目标地址摘要、秘密材料与启用状态。
- **事务 outbox 是强制约束**：业务动作只在同一事务内向 outbox 写入待发送记录；外部发送只能在事务提交成功后由发送器执行。任何在事务内发起 HTTP 或 SMTP 调用的路径都是缺陷。
- 业务事务回滚后不得存在可发送的 outbox 记录；这是可自动验证的红线。
- 发送失败进入有限重试：有最大重试次数与退避策略；达到上限后进入失败终态并停止重试，避免无限重试。
- 重试是幂等的：同一 outbox 记录重复投递不得以网络抖动为理由放大成多条实际通知；同一记录只允许有一个明确的终态。
- 通知内容必须脱敏：不含 token、密码、Cookie、Authorization 或完整正文；正文相关事件只携带代理名、时间与结果摘要。
- 目标配置中的秘密（Webhook secret、邮箱密码）按已接受风险明文静态存储，**不得声称已加密**；但 API、日志、UI 与审计必须脱敏或掩码。
- 目标秘密只在创建或更新时接收，读取时必须掩码。
- 提供显式测试通知入口 `POST /api/v1/notification-targets/{targetId}:test`，发送的是明确的测试事件，不伪造业务事件。
- 发送过程不得阻塞业务路径，也不得阻塞数据面：发送器在事务之外独立运行，有自己的并发与超时上限。
- Webhook 目标必须防 SSRF：限制协议、端口、地址范围，禁止内网与回环目标，除非管理员显式确认的风险场景中另有取舍（P1 默认拒绝）。
- 通知目标的增删改需审计；通知发送结果进入日志与 FR-14 的错误类指标。

- 范围内：
  - Webhook 与邮件两类通知目标的模型与管理端点。
  - 事务 outbox 的写入、提交后触发、发送、重试、退避与终态。
  - 通知事件的内容模型与脱敏约束。
  - 目标秘密的存储边界与掩码展示。
  - 测试通知入口与发送结果查询。
  - 通知失败与重试的日志、指标与运维可见性。
- 范围外：
  - **配置文件作为配置真源**：已被 ADR-0004 拒绝；通知目标与重试参数只存 SQLite 并经管理 API 变更。
  - QQ 通知及其他即时通讯渠道（P2，FR-20）。
  - 通知目标的静态加密：项目不提供，不得声称。
  - 消息队列、外部任务队列、定时重投服务与分布式投递保证（P3）。
  - 多租户或按角色的通知订阅与分级路由（P3）。
  - 通知模板引擎、多语言模板与用户自定义模板语法。
  - 告警规则引擎与阈值判定：属 FR-14 提供指标后的独立议题。
  - 出站代理、Webhook 签名验证以外的双向认证的具体密码套件配置。

## 3. 设计

### 3.1 模块与依赖方向

- Core 侧：**完全不参与通知**。Core 不调用 Webhook、不发邮件、不知道通知目标的存在；相关真相只经 FR-27 的有界事件通道以外壳可见的形式回流。
- jrps 侧：持有通知目标模型、outbox 模型、发送器与管理端点。业务编排在同一事务内写业务数据与 outbox，提交后由发送器异步接管。
- jrpc 侧：P1 不向管理员发送通知；本地应用失败通过回执上报服务端，由服务端决定是否通知。jrpc 不持有 SMTP 或 Webhook 目标。
- 依赖方向：外壳 → Core 单向。发送器不得反向让 Core 等待发送结果。

### 3.2 事务 outbox 流程

```text
业务动作（如配置应用失败、客户端 token 变更、容量触顶、正文清理异常）
   │
   ▼
┌── 同一业务事务 ────────────────────────┐
│ 写业务结果表                            │
│ 写 outbox 待发送记录（目标、事件类型、脱敏载荷）│
│ 提交                                   │
└───────────────────────────────────────┘
   │ 提交成功
   ▼
发送器轮询或收到唤醒
   │
   ├── 发送成功 ──▶ 记录发送成功 · 移出待发送 · 写 INFO 日志
   │
   └── 发送失败 ──▶ 记录失败原因摘要 · 递增重试次数 · 按退避重新入队
                     │ 达到重试上限
                     ▼
                   失败终态 · 停止重试 · 写 ERROR 日志 · 计入错误指标
```

硬边界：

- **禁止事务内远程调用**：写入 outbox 与发送是两个不可逆分离的阶段，发送器不持有尚未提交事务的句柄。
- **提交后触发**：任何未提交的 outbox 记录对发送器不可见，实现方式上以事务隔离保证，不以应用层约定保证。
- **回滚即不存在**：事务回滚后该批 outbox 记录随之消失，发送器永远不会拿到它们。
- **发送失败不影响业务结果**：业务结果已提交，发送失败只影响通知可达性，不改变业务事实。

### 3.3 重试与幂等

| 状态 | 含义 | 迁移条件 |
|---|---|---|
| pending | 已提交待发送 | 初始状态 |
| sending | 发送器已取出正在发送 | 取出时标记；进程崩溃后按租约超时回到 pending |
| sent | 发送成功并记录结果 | 目标返回成功响应 |
| retrying | 发送失败，等待退避后重试 | 重试次数未达上限 |
| failed | 达到重试上限，停止重试 | 重试次数达到上限 |
| discarded | 目标被禁用或删除，或事件已过期不再有意义 | 目标不可用或管理员禁用 |

- 最大重试次数与退避策略有明确上限并可实现为有限序列；退避带抖动，避免同目标重试风暴。
- 幂等边界：每条 outbox 记录有稳定事件标识；网络超时后重投同一事件标识视为同一次投递。远端是否去重取决于目标实现，JRP 保证不因自身重试把一条记录拆成多条投递尝试以外的事实。
-租约机制：`sending` 状态带租约时间，超时未被确认则回到 `pending` 重新投递，租约到期重投不得导致同一记录并发双发。
- 失败终态必须留下可运维证据：失败次数、最后一次脱敏错误摘要与最终停止时间。

### 3.4 渠道实现要点

**Webhook**：

- 出站 HTTP 请求使用明确的方法、超时与大小上限；请求体为 UTF-8 JSON，含事件类型、发生时间、脱敏载荷与事件标识。
- 目标 URL 校验协议、主机、端口与路径，禁止指向回环、链路本地与私有地址范围，防 SSRF；重定向不得被自动跟随到被禁止范围。
- 支持秘密签名：使用目标配置的 secret 生成签名头，便于下游验证来源。secret 本身不出现在请求体、日志或错误信息中。
- 非 2xx 响应、超时、TLS 失败与 DNS 失败统一归类为可重试或不可重试：4xx 类中明确无效目标与鉴权问题判为不可重试，直接进失败终态；超时与 5xx 判为可重试。

**邮件**：

- 经 SMTP 发送，支持显式主机、端口、发件人、收件人与安全传输选项；连接与发送有超时。
- 邮件主题与正文为 UTF-8 中文；正文只含脱敏摘要，不含凭证与正文内容。
- SMTP 凭据按已接受风险明文静态存储；读取接口只返回掩码，日志不打印密码。
- 收件人数量有上限；不得把通知内容抄送到未在配置中的地址。

### 3.5 秘密与脱敏

| 数据 | 静态存储 | API 读取 | 日志 | UI |
|---|---|---|---|---|
| Webhook secret | 明文（已接受风险） | 掩码 | 禁止出现 | 掩码，仅一次创建后可不见 |
| 邮箱密码 | 明文（已接受风险） | 掩码 | 禁止出现 | 掩码 |
| 目标 URL | 明文 | 脱敏摘要，隐藏凭据部分 | 只允许目标标识 | 掩码敏感查询串 |
| 通知载荷 | 库内明文但已脱敏 | 只含脱敏字段 | 只含摘要 | 只含摘要 |

通知载荷脱敏矩阵：允许事件类型、发生时间、客户端标识、代理名、revision、阶段、结果类别与安全错误摘要；禁止 token、密码、Cookie、Authorization、完整正文与分段文件路径。

### 3.6 管理接口与审计

- `GET/POST/PATCH/DELETE /api/v1/notification-targets`：管理目标；读取时秘密掩码。
- `POST /api/v1/notification-targets/{targetId}:test`：显式测试通知，记录为测试事件而非业务事件。
- 目标增删改需管理员会话与 CSRF，并写入审计；测试通知同样审计。
- 删除目标时处理未发送记录：在途与本目标相关的待发送记录转入 discarded 并有审计记录，不得静默丢失。
- 发送结果可通过 outbox 状态与日志查看；API 不返回 SMTP 或 Webhook 的秘密。

## 5. 验收标准

正常路径：

- 自动化：业务动作成功后同一事务写入 outbox；提交后发送器取出并发送成功，记录 sent 与时间。
- 自动化：Webhook 目标收到符合契约的 JSON 请求，含事件类型、发生时间、事件标识与脱敏载荷。
- 自动化：邮件目标收到中文主题与正文，内容只含脱敏摘要。
- 自动化：测试通知入口发送的是明确的测试事件，不伪造业务事件，且写入审计。

边界：

- 自动化：目标秘密在读取 API、日志与 UI 中一律掩码；更新秘密后旧秘密不再出现在任何输出中。
- 自动化：目标被禁用或删除时，相关在途记录转入 discarded 并有审计，不发生静默丢失。
- 自动化：退避与抖动生效，重试间隔递增；达到最大重试次数后进入 failed 且不再重试。
- 自动化：同一 outbox 记录在租约超时后重投时不被并发双发；`-race` 下无竞态报告。
- 自动化：通知连接与发送超时受限于明确上限；目标无响应时不阻塞管理请求与数据面转发。

错误路径：

- 自动化：业务事务回滚后不存在可发送的 outbox 记录，发送器不会拿到该批记录。
- 自动化：代码中不存在"在持有未提交事务时发起远程发送"的路径（以注入式发送器断言）。
- 自动化：超时与 5xx 判为可重试并进入 retrying；明确无效的 4xx 鉴权失败判为不可重试并直接进入 failed。
- 自动化：DNS 失败、TLS 失败与连接被拒均产生脱敏错误摘要，并按既定归类落入 retrying 或 failed，摘要不含堆栈、秘密或内部地址。
- 自动化：日志、UI 与审计中不含 Webhook secret、邮箱密码或完整正文；对这三类值逐一构造用例断言。
- 自动化：Webhook 指向回环、链路本地与私有地址的请求被拒绝；重定向到被禁止范围不被跟随。
- 自动化：未认证访问通知端点返回 401；修改类请求缺少或错误 CSRF 返回 403 且无副作用。
- 自动化：达到失败终态的记录留下失败次数、最后脱敏错误摘要与最终停止时间，可被运维查询。

实机（需用户确认，S2 批次）：在一台机器上启动 jrps，配置一个公网可达的 HTTPS Webhook 接收端与一个真实邮箱 SMTP 目标；用本阶段已接入的写入点触发真实投递——通知目标的创建、更新或删除，或管理员登录连续失败达到阈值——确认通知到达、内容为中文脱敏摘要、Webhook 签名可校验；随后把 Webhook 目标改为不可达地址，确认重试按退避进行并在达到上限后停止，日志中无密码或 secret。

实机（需用户确认，随 FR-10 补验）：触发一次配置应用失败，确认对应通知到达且内容为中文脱敏摘要。

实机（需用户确认，token 变更）：**已通过**。轮换与吊销各自产生一条通知事件并进入投递链路，载荷为中文摘要且不含 token 值或摘要；同时确认审计中 `client_rotate` 与 `client_revoke` 两个动作首次有了写入点（FR-16 的挂起补验项）。配置应用失败那一半仍随 FR-10。

实机（需用户确认，Web 通知页展示）：已通过。通知页提供目标管理、测试通知与发送结果，失败终态展示失败次数、脱敏错误摘要与停止时间；浏览器实机验收 8 项全通过。

## 6. 风险与待定

### 6.1 已接入的写入侧业务动作

规格把「按事件类型订阅与分级路由」列为 P3，因此 P1 不建立事件类型到目标的映射：事件按广播投递给全部启用目标，且排除被本次动作变更的目标自身——发给它是自我指涉，该目标随后一旦停用或删除，记录会被清理扫掉，留不下任何东西。

| 业务动作 | 事件类型 | 说明 |
| --- | --- | --- |
| 通知目标创建 / 更新 | `notification_target_created` / `notification_target_updated` | 与业务写入同事务；排除被变更的目标 |
| 通知目标删除 | `notification_target_deleted` | **不指向目标**：删除是硬删除，指向已消失的目标会让记录以"投递失败"收场，而 `failed` 会被读成投递出了问题，真实原因却是目标已不存在 |
| 管理员登录连续失败达阈值 | `admin_login_failure_limit_reached` | 仅在跨过阈值的那一次写入：单次失败是噪声，达到阈值才意味着有人在尝试爆破凭据。达到阈值后请求被限流拦在校验之前，故一个锁定窗口最多触发一次 |

未接入的写入点：配置应用结果属 FR-10、代理变更属 FR-11、容量触顶与正文清理异常属 FR-13/FR-14，均随对应 FR 补齐。

**已接入**：客户端 token 轮换与吊销（FR-07 交付后补齐）产生 `client_token_rotated` 与 `client_token_revoked` 事件，与业务写入同事务入队。载荷只含客户端名称、标识与动作，不含 token 值或摘要——通知渠道是外部系统，把凭据材料写到那里等于把秘密复制到不受控的位置。事件不排除任何目标：被变更的是客户端而非通知目标，不存在自我指涉。

### 6.2 风险与待定清单

- **风险**：明文存储 SMTP 密码与 Webhook secret，数据目录或备份泄露即暴露。缓解方式是最小权限、掩码输出、按需轮换与审计；文档与 UI 不得声称加密。
- **风险**：通知洪泛在大规模故障时会放大外部依赖压力。缓解方式是有限重试、退避抖动、每目标并发上限与必要时禁用目标。
- **风险**：SMTP 或下游服务长时间不可达会让 outbox 积压。缓解方式是失败终态止损、旧记录按保留策略清理，并在 FR-14 观察积压水位。
- **风险**：SSRF 防护过严可能挡住管理员确有正当理由的内网目标。P1 默认拒绝内网与回环；确有正当场景需在后续决策中评估，不在本功能私自放开。
- **已定**：实机验收的接收端改用公网对端，SSRF 防护与 SMTP 渠道的同源校验都不放开——§5 的实机条款相应改写为「配置一个公网可达的 HTTPS Webhook 接收端与一个真实邮箱 SMTP 目标」（接收端端口限 443/8443/9443）。不选"为验收放开内网白名单"这一支的理由是：验收便利不足以换取生产防护的削弱，且公网对端能顺带覆盖真实 DNS、真实 TLS 与重定向行为，比回环对端更接近真实部署形态。
- **待定**：最大重试次数、退避序列与租约时长的具体数值需在实现前定稿，暂按有限次与有界退避实现。
- **待定**：outbox 历史记录的保留天数需在 FR-16 的统一保留策略中确定，本功能暂不自行删除成功记录以外的历史。
- **待定**：是否需要在 Web 通知页展示逐次重试明细，取决于 FR-11 页面与发送结果查询形态的统一结果。
