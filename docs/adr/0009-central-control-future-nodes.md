# ADR-0009：P3 采用中心控制面与数据节点方向

## 状态

已接受

## 背景

长期部署可能需要跨地域或多入口扩展，但 P1 的目标是单机平台。若现在提前建立节点表、RPC、注册、选举或共享数据库，会把未验证的分布式需求带入当前模型；若完全忽略未来复用，又可能让 Core 与 jrps 控制面永久耦合。

## 决策

P3 的方向锁定为“中心控制面 + 多数据节点”：中央控制面持有数据库、用户、配置和 Web；数据节点作为新的可执行 module，只组合 Core 并接收版本化配置。P1 仅保持 Core 独立可组合，不定义任何节点网络协议或模型。

## 理由

- 中央真源便于统一配置、审计和用户管理。
- 数据节点靠近流量入口，适合未来横向扩展和故障转移。
- 先锁定边界、不锁定 RPC 细节，避免过早设计。
- 独立 Core 让未来节点复用数据面而不携带 Web/SQLite 控制面。

## 后果

- P1 禁止创建 `apps/node`、节点 RPC、节点注册、心跳表、调度字段、选举、分布式锁或共享数据库。
- P1 API、数据库和 Core 接口不预留空 node/cluster/tenant 字段。
- 真正进入 P3 前必须新增 ADR/spec，定义身份、配置协议、一致性、调度、故障转移和升级兼容。
- HA、RBAC、OIDC、外部数据库和对象存储只在 P3 需求成立后评估，不因本 ADR 自动获准。

## 备选方案

- **P1 同时实现分布式节点**：范围和风险过大，拒绝。
- **每个节点独立数据库且无中央真源**：配置与审计难以一致，拒绝。
- **把控制面继续嵌入每个数据节点**：重复管理能力并破坏职责边界，拒绝。
