# ADR-0001：独立实现官方 frpc 兼容能力

## 状态

已被 [ADR-0010](0010-portable-compatibility-baseline.md) 取代

## 背景

JRP 需要让官方 frpc 直接连接 jrps，同时项目采用 MIT 许可证并形成自身可维护的协议实现。兼容研究若直接复用参考项目源码、包结构、注释、错误文案或测试组织，会破坏版权边界与工程独立性。

用于理解公开线上行为的只读参考由开发环境自行提供检出位置（该位置不属于项目契约），兼容基线为 Git 提交 `e1f1d6ab1b591ec9b596f4b1b6a81cd2960c6314`。

## 决策

JRP 采用独立实现：只根据公开行为、JRP 自有协议规格和黑盒互操作证据实现兼容；不复制、改写、链接、导入 frp 源码或 Go package。

## 理由

- 固定参考提交可以让兼容范围和回归结果可重复。
- 独立规格避免把参考实现的内部设计误当作协议要求。
- 黑盒测试更接近用户真正关心的互操作结果。
- 清晰版权边界允许 JRP 按 MIT 许可独立演进。

## 后果

- Core 依赖图不得出现 `github.com/fatedier/frp`。
- 不复用参考仓库的注释、错误文案、目录结构、NAT 策略表或测试组织。
- 兼容性变更必须更新 `docs/PROTOCOL.md` 和 JRP 自有测试。
- 临时抓包、对比结果和外部二进制放入 `.tmp/`，不得入库。
- 独立实现成本更高，需要黄金帧、畸形输入、状态机和真实 frpc 测试共同覆盖。

## 备选方案

- **直接依赖 frp Go package**：实现快，但破坏 Core 独立性与许可边界，拒绝。
- **复制后修改源码**：难以证明独立实现，并长期承受上游结构耦合，拒绝。
- **完全不兼容官方 frpc**：降低实现成本，但失去核心产品价值，拒绝。
